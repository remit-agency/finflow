# S04 — Курси НБП: `resolveRate`, кеш таблиць у Firestore

> Статус: **дизайн затверджено користувачем 2026-10-26**, спека чекає перегляду.

## Мета

Дати застосунку відтворюваний курс валют для перерахунку в PLN за польським податковим правилом. Це серверний будівельний блок для S05 (запис операції зберігає знімок курсу), S07 (форма операції підставляє курс) і S12 (курсові різниці). Екрана в S04 немає.

## Вихідний стан (перевірено)

- Курсів у коді немає. Валюти застосунку: PLN, EUR, USD, UAH (`lib/utils`, правила Firestore).
- Roadmap (`2026-10-22-finflow-roadmap.md`): курс NBP таблиці A знімається при першому записі; правило попереднього робочого дня; без cron, ліниві курси та кеш у Firestore.
- Перевірено запитом до `https://api.nbp.pl/api/exchangerates/tables/A/{from}/{to}/?format=json` (2026-10-26):
  - відповідь: масив `{table, no, effectiveDate, rates[{currency, code, mid}]}`; 32 валюти, UAH і EUR є;
  - діапазон до 93 днів, довший дає 400; діапазон у майбутньому дає 400; минулий діапазон без таблиць дає 404;
  - вихідні й свята не мають таблиць (у жовтні 2026: 18 таблиць за 18 робочих днів).

## Рішення

| Питання | Рішення |
|---|---|
| Політика курсу | Одна, без налаштувань: таблиця A з найбільшою `effectiveDate` **строго меншою** за дату операції. Понеділок бере п'ятницю, свято бере останню опубліковану таблицю, майбутня дата бере останню опубліковану. Календар свят не потрібен: дні без таблиць відсіюються самі. |
| Параметр `policy` | Немає (YAGNI). Сигнатура `resolveRate(from, to, date)`. Відхилення від roadmap, де згадано `policy`. |
| Ручні курси, «на дату», таблиця B, інші провайдери | Поза S04. |
| Результат | Знімок для зберігання в операції (S05): `{ rate, from, to, requestedDate, rateDate, tableNo, source: 'NBP_A' }`. |
| Точність | `rate` округлюється до 8 знаків (як у Finmap). |
| Кеш | Firestore, колекція `fxTables`, один документ на місяць. |

## Модель

### Дати

Усі дати в S04 це рядки `YYYY-MM-DD` (доба UTC, як і дати операцій у застосунку). «Сьогодні» для оновлення кешу береться з `todayUtcDay()` (варшавська дата).

### Формули

`mid(X)` це PLN за одну одиницю X з таблиці A на `rateDate`.

- `from == to`: `rate = 1`, до НБП не звертаємось, `rateDate = requestedDate`, `tableNo = null`.
- `X → PLN`: `mid(X)`.
- `PLN → X`: `1 / mid(X)`.
- `X → Y`: `mid(X) / mid(Y)`.

Результат округлюється до 8 знаків. Обидві валюти беруться з однієї й тієї самої таблиці.

### Пошук таблиці для дати D

1. Цільовий момент: найбільша `effectiveDate < D`.
2. Беремо місячний документ для місяця `D - 1 день`; якщо в ньому немає таблиці раніше D (наприклад, на початку місяця), беремо попередній місяць, і так до 2002-01 (перша таблиця A: 2002-01-02). Якщо таблицю не знайдено: помилка `no_rate_before`.

### Кеш `fxTables/{YYYY-MM}`

Документ: `{ month, tables: [{ no, effectiveDate, rates: { EUR: 4.4026, … } }], fetchedAt, complete }`.

- Місяць, який уже закінчився до сьогоднішньої варшавської дати, після завантаження позначається `complete: true` і не оновлюється ніколи.
- Поточний місяць: `complete: false`, оновлюється, якщо `fetchedAt` старший за 1 годину.
- Завантаження: один запит НБП на межі місяця (до 31 дня, у межах ліміту 93). Відповідь 404 для минулого місяця без таблиць дає порожній `tables`.
- Якщо оновити не вдалося (НБП недоступний або відповів сміттям), застарілий документ використовується лише тоді, коли в ньому вже є таблиця з `effectiveDate >= D`: тоді результат гарантовано правильний. Інакше помилка `provider_unavailable`.
- Запис кешу ідемпотентний (`set` повного документа); гонка двох запитів дає ту саму відповідь НБП.

### Правила Firestore

Колекція `fxTables` закрита для клієнтів (читання й запис заборонені). Читає й пише лише сервер через Admin SDK. Явного `match` не потрібно, але rules-тест доводить відмову.

## Інтерфейс

### Модулі (`lib/server/fx/`, лише сервер)

- `nbp.ts`: клієнт НБП (`fetchTables(fromDay, toDay)`, таймаут, перевірка форми відповіді, коди помилок).
- `store.ts`: читання й запис `fxTables` через Admin SDK.
- `resolve-rate.ts`: чиста логіка вибору таблиці й формул (`pickTable`, `crossRate`), без I/O.
- `index.ts`: `resolveRate(from, to, date)`, що збирає кеш, НБП і чисту логіку.
- `import 'server-only'` на модулях з I/O (діє правило `check:server-imports`).

### Роут `GET /api/rates?from=EUR&to=PLN&date=2026-10-26`

- Потрібна сесія (`requireUser`); компанія не потрібна, курси публічні.
- Валідація: `from`, `to` 3 великі латинські літери, `date` дійсна `YYYY-MM-DD` (рік 2002..рік+1), зайві параметри 400.
- 200 `{ rate, from, to, requestedDate, rateDate, tableNo, source }`, `Cache-Control: private, max-age=300`.
- 400 `invalid_params`; 404 `unsupported_currency` (код не в таблиці A) або `no_rate_before`; 503 `provider_unavailable`. Помилка НБП не віддає клієнту сирого тексту.

### Підтримувані валюти

Будь-яка, що є в таблиці A на потрібну дату (PLN синтетична, `mid = 1`). Список валют застосунку не обмежується в S04.

## Тестування

- Unit на фікстурах реальних відповідей НБП (зберігаємо уривки в `tests/fixtures/nbp/`): понеділок бере п'ятницю; 1 листопада (неділя) і 11 листопада (свято) бере останню таблицю; Різдво; Великдень; 1-ше число місяця (перехід місяця й року); майбутня дата; дата раніше 2002; невідома валюта.
- Property-тести (`fast-check` або власні випадкові цикли): `A→B × B→A ≈ 1` (з урахуванням округлення 8 знаків), `A→C ≈ A→B × B→C`, результат монотонний за вибором таблиці.
- Кеш: промах, влучання, завершений місяць не оновлюється, поточний оновлюється після години, відмова НБП при застарілому кеші (обидві гілки).
- Rules-тест: клієнт не читає й не пише `fxTables` (аутентифікований і ні).
- Тест роуту з підміненим `fetch` і Admin-сховищем на емуляторі: 401 без сесії, 400, 404, 503, 200.
- Ручний скрипт `scripts/check-nbp.mjs` (не в CI): реальний запит і порівняння з очікуванням для відомої дати.
