# S06 — Контрагенти: NIP, IBAN, Біла ліста MF, ZUS і Urząd Skarbowy

> Статус: **реалізовано в гілці `s06-counterparties`, чекає мерджа.** Залежить від S05 (серверний запис, аудит, `counterpartyId` в операції). Форму операції переробляє S07, тут вона не змінюється.

## Мета

Дати кожній компанії довідник контрагентів із перевіреними реквізитами: NIP з контрольною сумою, рахунки IBAN, статус VAT і автозаповнення з Білої ліста Міністерства фінансів. Дубль за NIP або назвою відхиляється. ZUS і Urząd Skarbowy існують у кожній компанії одразу. Операції можуть посилатись на контрагента, і це посилання завжди живе.

## Вихідний стан (перевірено 2026-10-27)

- Колекції контрагентів немає. Операція має необов'язкове `counterpartyId`; сервер S05 перевіряє лише, що це рядок-ідентифікатор (`lib/domain/ledger/input.ts`), існування контрагента не перевіряється.
- Серверний запис і аудит вже є (`lib/server/ledger`: транзакція Admin SDK, `auditData`, `toHttpError`, `readJsonBody`). Правила Firestore закривають клієнтський запис до рахунків, операцій, rollups і audit.
- Категорії засіваються на клієнті (`seedDefaultCategories`), компанія створюється на сервері (`lib/server/orgs.ts`, транзакція).
- Публічний API Білої ліста `https://wl-api.mf.gov.pl/api/search/nip/{nip}?date=YYYY-MM-DD` відповідає без ключа (перевірено 2026-10-27): повертає `name`, `nip`, `statusVat`, `regon`, `krs`, `residenceAddress`, `workingAddress`, `accountNumbers[]`, `hasVirtualAccounts`; помилка NIP це HTTP 400 `{"code":"WL-115"}`.

## Рішення

1. **Запис лише через сервер**, як у S05: Admin-транзакція разом з аудитом. Клієнт у `counterparties` і `counterpartyKeys` не пише.
2. **Унікальність через ключі.** Для кожного контрагента в тій самій транзакції створюються документи-ключі `counterpartyKeys/nip_{nip}` і `counterpartyKeys/name_{нормалізована назва}`. Їхнє існування й є забороною дубля: два одночасні запити не можуть обидва пройти.
3. **Джерело NIP лише Біла ліста MF.** GUS REGON поза обсягом. Контрагента без VAT (фізособа) вводять вручну.
4. **ZUS і Urząd Skarbowy** це звичайні записи з маркером `kind` (`zus`, `us`), їх можна редагувати й архівувати. Засіваються при створенні компанії й одним ідемпотентним скриптом існуючим.
5. **Видалення не існує, є архівація.** Контрагент з посиланнями в операціях не має зникати. Архівний не пропонується для вибору, але показується в історії.
6. **Інтерфейс:** розділ налаштувань «Контрагенти» і багаторазовий `CounterpartyPicker`; у форму операції не підключається (S07).

## Модель

`organizations/{org}/counterparties/{id}`:

| Поле | Тип | Примітка |
|---|---|---|
| `schemaVersion` | `1` | |
| `name` | рядок, 1–200 | обрізаний, внутрішні пробіли стиснуті |
| `nip` | рядок з 10 цифр, необов'язково | без префікса `PL`, дефісів і пробілів; контрольна сума (ваги 6,5,7,2,3,4,5,6,7, сума mod 11, 10 недопустимий) |
| `ibans` | об'єкти `{ iban, onWhitelist }`, до 20 | `iban`: нормалізований NRB, 26 цифр без пробілів і префікса `PL`, контрольна сума mod 97. `onWhitelist`: `true`, `false` або `null` (не перевірено), виставляє сервер |
| `address` | рядок, необов'язково | з Білої ліста: робоча адреса, інакше адреса проживання |
| `vat` | `{ status, checkedOn }`, необов'язково | `status`: `active` (Czynny), `exempt` (Zwolniony), `unregistered` (Niezarejestrowany); `checkedOn` це день перевірки `YYYY-MM-DD`; виставляє лише сервер, клієнт це поле не надсилає |
| `kind` | `zus` або `us`, необов'язково | тільки у двох системних записів |
| `archived` | булеве | типово `false` |
| `createdAt`, `updatedAt` | Timestamp | |

`organizations/{org}/counterpartyKeys/{key}`: `{ counterpartyId }`. Ключ NIP це `nip_{10 цифр}`. Ключ назви це `name_` + літери й цифри в нижньому регістрі, де кожна інша послідовність символів замінена одним `_` (без `encodeURIComponent`). Діакритика латиниці прибирається (`ł` це `l`), решта комбінувальних знаків, наприклад наголос, теж відкидається, а `й` і `ї` лишаються окремими літерами; довжина назви не більше 200. Ключі закриті для клієнта повністю (читання теж).

Рахунки IBAN не мають власних ключів: один рахунок може належати двом контрагентам (наприклад, платіжний агент).

**Обмеження:** до 5000 контрагентів на компанію (помилка `limit`).

## Сервер

Модуль `lib/server/counterparties` (поруч із `lib/server/ledger`; не змішувати з леджером, але використовувати `auditData`, `toHttpError` і `readJsonBody`). Чисті правила (нормалізація, NIP, NRB, ключі, розбір відповіді) у `lib/domain/counterparties`.

**Роути** (`app/api/orgs/[orgId]/counterparties/...`, ролі: читання всі члени, запис owner і accountant, viewer лише читає):

- `POST .../counterparties`: створює. Помилки: 400 `invalid_input` (з назвою поля), 409 `duplicate` (з `field: 'nip' | 'name'` і `existingId`), 409 `limit`.
- `PATCH .../counterparties/{id}`: змінює `name`, `nip`, `ibans`, `address`, `archived`. Поле `vat` клієнт не надсилає: сервер виставляє його сам за результатом запиту до Білої ліста під час збереження (коли є `nip` і змінився NIP або список IBAN). Зміна NIP чи назви в тій самій транзакції переносить ключі (видаляє старий, створює новий; конфлікт це `duplicate`). `kind` змінювати не можна. Додаткова помилка: 409 `conflict` при одночасному редагуванні того самого контрагента.
- `GET .../counterparties/lookup?nip=...`: запит до Білої ліста (нижче), нічого не пише. Дозволений лише ролям owner і accountant (це підготовка запису).
- Видалення немає: є `archived: true`. Контрагент з `kind` можна архівувати, а скрипт засівання при наступному запуску його не створює повторно (шукає за `kind`, не за назвою).

**Біла ліста.** `lookupNip(nip, today)`: сервер викликає API з `date` = сьогодні за Варшавою, таймаут 8 с, один повтор після мережевої помилки або таймауту (помилка HTTP чи нечитабельна відповідь не повторюються). Відповідь розбирається суворо (невідомі поля ігноруються, відсутні обов'язкові дають `lookup_unavailable`). Результат: `{ found, name, address, vatStatus, ibans, checkedOn }`. `statusVat` мапиться: `Czynny` → `active`, `Zwolniony` → `exempt`, `Niezarejestrowany` → `unregistered`, інше → помилка `lookup_unavailable`. NIP, якого немає в реєстрі, це `found: false` (а не помилка). NIP спершу перевіряється локально; неправильний NIP це 400 `invalid_input` без виклику MF (тому `WL-115` до клієнта не доходить). Помилки MF і таймаут це 502 `lookup_unavailable`, ручне введення при цьому лишається можливим. Тіло відповіді MF у логи не пишеться.

**Ліміт запитів.** Не більше 30 запитів до Білої ліста на користувача за хвилину і 300 за годину (рахуються і виклик `lookup`, і виклики білого списку з create та update; дубль при створенні відсікається до звернення до MF); спільний лічильник у `lib/server/rate-limit` (Firestore-документ `rateLimits/{scope}_{uid}_{window}_{bucket}` з полем `expiresAt` і транзакційним інкрементом; TTL-політика Firestore для їхнього очищення це наступний крок) також підключається до `/api/rates` (ліміт 120 на хвилину і 1200 на годину; закриває відкритий пункт «rate limit для /api/rates»). Ядро лічильника (`lib/server/rate-limit.ts`, приймає Firestore) відокремлене від обгортки (`lib/server/rate-limit-guard.ts`, використовує `getAdmin`), щоб інтеграційні тести не імпортували `server-only` код. Перевищення це 429 `rate_limited`.

**Перевірка IBAN проти білого списку.** Вона виконується на сервері при створенні й зміні, якщо контрагент має NIP: запит `lookup` порівнює кожен введений IBAN зі списком `accountNumbers`. Результат записується в `onWhitelist` кожного IBAN (`null`, якщо MF недоступний або NIP не знайдено). Якщо в компанії `hasVirtualAccounts: true`, IBAN, якого немає в списку, теж позначається `null` («не перевірено»), а не `false`: у неї можуть бути рахунки, яких список не показує. Це лише ознака для інтерфейсу, вона нічого не блокує. Без NIP перевірка не виконується.

**Зв'язок з операціями (зміна в S05-коді).** `createTransaction` і `updateTransaction` у `lib/server/ledger/write.ts`, якщо є `counterpartyId`, читають документ контрагента в тій самій транзакції. Немає документа це `LedgerError('counterparty_not_found')` (HTTP 422 у `toHttpError`, як `account_not_found` і `category_not_found`). Архівованого контрагента не можна призначити новій операції (422 `counterparty_archived`), але існуюча операція з ним лишається чинною; редагування операції без зміни `counterpartyId` архівного не перевіряє.

**Засівання.** `seedSystemCounterparties(tx, orgId)` створює `ZUS` (`kind: 'zus'`) і `Urząd Skarbowy` (`kind: 'us'`) без NIP і IBAN. Викликається в транзакції створення компанії (`lib/server/orgs.ts`; для нової компанії записи створюються без записів аудиту; їх пише скрипт засівання для існуючих) і скриптом `npm run seed:counterparties` (за зразком `migrate:ledger`: dry-run за замовчуванням, `--apply`, `--project=finflow-e94b5` обов'язковий на проді, ідемпотентний, шукає за `kind`, не за назвою). Назви однакові в усіх мовах (власні назви).

**Аудит.** Дії `counterparty.create` і `counterparty.update` (архівація це update) записуються в `audit` тією самою транзакцією.

## Правила Firestore

`counterparties`: читання для всіх членів компанії, клієнтський запис заборонено. `counterpartyKeys` і кореневий `rateLimits`: усе заборонено клієнту (читання теж). Тести правил: viewer, accountant, owner і не-член не можуть писати; не-член не читає; ключі недоступні нікому з клієнтів.

## Інтерфейс

- **Розділ «Контрагенти»** в налаштуваннях (доступний усім членам; редагування лише owner і accountant): список з пошуком за назвою й NIP, фільтр «показати архівні», кнопка «Додати».
- **Форма:** поле NIP з кнопкою «Підтягнути дані» (заповнює назву, адресу й статус VAT; рахунки IBAN форма підставляє лише тоді, коли Біла ліста повертає від 1 до 20 рахунків і в формі їх ще немає (у великої компанії їх сотні: користувач вводить рахунок, на який платить, а сервер позначає його); користувач бачить результат і підтверджує); список IBAN з бейджем «у білому списку / немає в білому списку / не перевірено»; бейдж статусу VAT з датою перевірки; помилка `duplicate` показує існуючого контрагента посиланням.
- **`CounterpartyPicker`:** комбобокс з пошуком по активних контрагентах, створення «на льоту» за NIP (відкриває форму в діалозі). Контрольований компонент (`value`, `onChange`), без залежності від форми операції; S07 підключає його.
- Мови PL, EN, UA; усі тексти в каталогах повідомлень, мовою інтерфейсу. `kind` дає локалізований підпис («Системний»).

## Тестування

- **Юніт:** нормалізація назви й ключів (діакритика, `ł`, регістр, пробіли), контрольна сума NIP (відомі правильні й помилкові), NRB mod 97, розбір відповіді Білої ліста на записаних фікстурах (знайдений платник, не знайдений, відмова), мапінг статусів VAT, ліміт запитів, HTTP-мапінг помилок.
- **Інтеграційні (емулятор Firestore):** два одночасних створення з однаковим NIP або назвою дають рівно один запис і один `duplicate`; зміна назви переносить ключ; зміна NIP на зайнятий це `duplicate` без побічних змін; архівований відсікається від нових операцій; `createTransaction` з неіснуючим контрагентом дає `counterparty_not_found`; засівання ідемпотентне.
- **Правила:** як вище.
- **e2e:** створити контрагента вручну; створити за NIP (відповідь MF підставляється заглушкою на рівні сервера); дубль показує помилку; архівувати й відновити; сторінка PL/EN/UA.
- **Живий виклик Білої ліста:** одноразова ручна перевірка проти справжнього API перед мерджем, результат у PR (CI на мережу не покладається).

## Розгортання

1. Merge, Vercel, правила Firestore (тільки нові колекції закриті, наявні не змінюються).
2. `npm run seed:counterparties` dry-run, потім `--apply` на проді (потребує окремого «ок» власника; зміни лише додають документи).
3. Індекси не потрібні: клієнт читає всю колекцію компанії (до 5000 записів) і шукає та фільтрує архівних локально.

## Поза обсягом

GUS REGON, масовий імпорт контрагентів (S14), автопризначення контрагента операціям (S10), звіти й дебіторка за контрагентами (S19), підключення вибору контрагента до форми операції (S07), контактні особи, умови оплати, перевірка NIP через VIES для іноземних контрагентів.

## Відомі наступні кроки (follow-ups)

- Нічна синхронізація статусу VAT і білого списку (S18): зараз статус це знімок на день перевірки.
- Фізособа без NIP і іноземний контрагент: поки лише ручне введення, ключ унікальності тільки за назвою.
- Об'єднання дублів, що виникли поза системою (імпорт, S14).
- TTL-політика Firestore для `rateLimits` (поле `expiresAt`): без неї лічильники лишаються в базі.
- `CounterpartyPicker` не має браузерного тесту, доки S07 не підключить його до форми операції.
- Гілка `conflict` (одночасне редагування одного контрагента) не має автоматичного тесту.
