# S05 — Рушій обліку v2: серверний запис, дві дати, rollups, аудит

> Статус: **реалізовано в гілці `s05-accounting-engine`, чекає мерджа.** Рішення, додані під час деталізації й не показані на етапі дизайну, винесено в розділ «Додані під час деталізації».

## Мета

Зробити так, щоб гроші в застосунку були правильними за побудовою:

- баланс рахунку **завжди** дорівнює початковому залишку плюс сума фактичних операцій;
- кожна операція має **дві дати** (дата платежу й дата визнання, плюс режим «період визнання»), і підсумки ведуться окремо за кожною;
- звіти (S12) читають готові підсумки, а не всі операції;
- кожна зміна має слід у журналі аудиту.

Зараз це не так: `updateTransaction` не чіпає баланс, `createTransaction` оновлює баланси окремими запитами без атомарності, переказ користується полем `counterpartyId` як «рахунком призначення». Знайдено власником 2026-10-26 (баланс Monobank 1234,50 проти суми операцій 1234,60).

## Вихідний стан (перевірено)

- Операції пишуться клієнтом: `lib/firebase/transactions.ts` (batch + окремі `updateAccountBalance`), правила Firestore дозволяють запис ролям owner/accountant.
- `Transaction`: `date: Date`, `amount: number` (десяткове), `type`, `categoryId`, `counterpartyId`, `isRecurring`, `projectId`, `tags`, `fileUrls`. Однієї дати, статусу й курсу немає.
- Звіти (`lib/utils/analytics.ts`) читають усі операції й рахують у браузері.
- Банківського ingest ще немає (S09), тому всі наявні операції введені вручну або тестові.
- S04 дає серверний `resolveRate(from, to, date)` зі знімком `{rate, rateDate, tableNo, source, final}`.

## Рішення

| Питання | Рішення |
|---|---|
| Хто пише | Лише сервер. Рахунки, операції, rollups, аудит пишуться через API в одній транзакції Firestore (Admin SDK). Клієнт їх лише читає. Категорії лишаються клієнтськими. |
| Гроші | Цілі числа в мінімальних одиницях (`…Minor`, соті частки валюти). Усі валюти застосунку (PLN, EUR, USD, UAH) мають 2 знаки. Клієнтський шар перетворює в числа з десятковою частиною, екрани не змінюються. |
| Баланс | `balanceMinor = openingMinor + Σ ефектів фактичних операцій`. Зберігається, оновлюється `increment`, перевіряється `verifyLedger`. |
| Планові операції | `status: 'planned'` не змінює баланс і не потрапляє в rollups (їх читає прогноз S13 напряму). Перехід `planned → actual` робить звичайний PATCH. |
| Дві дати | `paymentDate` (дата платежу) і `accrual` (`{mode:'date', date}` або `{mode:'period', from, to}`). Обидві це рядки `YYYY-MM-DD` (доба, як у S04). За замовчуванням дата визнання дорівнює даті платежу. |
| Період | Сума розкладається по календарних місяцях періоду пропорційно кількості днів, залишок після цілочисельного ділення йде в останній місяць. Довжина періоду не більше 36 місяців. |
| Курс | У валюті компанії (`org.currency`) знімки не потрібні. Для іншої валюти: окремий знімок для дати платежу і для дати визнання (один, якщо дати збігаються). Дата для знімка визнання: `accrual.date` (для періоду `accrual.from`), обмежена зверху сьогоднішнім днем, тому знімок завжди `final`. Нефінальні знімки не зберігаються. Планова операція знімків не має. |
| Базові суми | `base = round(amountMinor × rate)` (півці від нуля), окремо для `payment` і `accrual`. Переказ базових сум не має (він не входить у P&L; курсові різниці S12). |
| Аудит | Колекція `audit`, запис у тій самій транзакції. Читає власник. |
| Ідемпотентність | `POST` приймає необов'язковий `clientId`: він стає id документа, повтор повертає наявну операцію (захист від подвійного кліку). |
| Перевірка й перебудова | `verifyLedger` (лише читання, повертає розбіжності) і `rebuildLedger` (запис підсумків з нуля). Для власника через `POST …/ledger/rebuild`. |

## Додані під час деталізації

1. **Захист від одночасного перебудування.** Документ `organizations/{org}/ledger/lock` (закритий для клієнтів). `rebuildLedger` бере оренду на 5 хвилин, будь-який запис операції в цей час відповідає 409 `ledger_busy`. Кожен запис читає цей документ (одне додаткове читання).
2. **Заморожування валюти компанії.** Базова валюта визначає всі базові суми, тому її не можна міняти, коли є операції. Зміна назви й валюти компанії йде через `PATCH /api/orgs/{orgId}`; валюту сервер відхиляє з 409 `currency_locked`, якщо в компанії є хоча б одна операція. Браузер більше взагалі не оновлює документ компанії (правила Firestore не мають `update` для `organizations/{id}`): назва й валюта йдуть лише через `PATCH /api/orgs/{orgId}`.
3. **Видалення й валюта рахунку.** Рахунок з операціями (як `accountId` або `toAccountId`) видалити не можна (409 `account_has_operations`), валюту такого рахунку змінити не можна (409).
4. **`tsx` у devDependencies.** Міграція виконується скриптом TypeScript, що використовує той самий доменний код, що й сервер (без дубля логіки).
5. **Стара схема не читається.** Клієнтський мапер приймає лише `schemaVersion: 2`; інші документи пропускаються з лічильником у лозі. Тому міграція йде до розгортання (див. нижче).

## Модель

### Рахунок (`organizations/{org}/accounts/{id}`)

`{ orgId, name, type, currency, color, openingMinor, balanceMinor, schemaVersion: 2, createdAt, updatedAt }`. Поле `balance` зі старої схеми не чіпається міграцією й ігнорується (прибирається окремим кроком після розгортання).

Редагування `openingMinor` змінює `balanceMinor` на ту саму різницю. Створення: `balanceMinor = openingMinor`.

### Операція (`organizations/{org}/transactions/{id}`)

```
type            'income' | 'expense' | 'transfer'
status          'actual' | 'planned'
accountId       рахунок (для переказу: звідки)
amountMinor     ціле > 0, у валюті рахунку
currency        = валюта рахунку (сервер звіряє)
toAccountId     лише переказ
toAmountMinor   лише переказ; для однакових валют дорівнює amountMinor
toCurrency      лише переказ
paymentDate     'YYYY-MM-DD'
accrual         { mode: 'date', date } | { mode: 'period', from, to }
categoryId      лише дохід/витрата; категорія існує, тип збігається
counterpartyId  необов'язково (S06), тепер лише контрагент
description, isRecurring, projectId, tags, fileUrls   як було
fx              { payment?: Snapshot, accrual?: Snapshot }   лише actual у не-базовій валюті
base            { payment: minor, accrual: minor }           лише коли є fx
schemaVersion   2
createdAt, updatedAt, createdBy, updatedBy
```

Обмеження: `amountMinor` ≤ 10^13; `description` ≤ 500 символів; ≤ 20 тегів; ≤ 10 `fileUrls`. Дати: рік не раніше 2000. `actual`: `paymentDate` ≤ сьогодні (за Варшавою); `planned`: будь-яка дата не далі 10 років уперед. Переказ без категорії; переказ на той самий рахунок відхиляється.

### Чисті функції (`lib/domain/ledger/`, без I/O)

- `validateTransaction(draft, ctx)` → `Result<Transaction, LedgerError[]>`: усі правила вище.
- `balanceEffects(tx)` → `{ [accountId]: deltaMinor }`: дохід `+amount`, витрата `−amount`, переказ `−amount` на `accountId` і `+toAmount` на `toAccountId`, планова `{}`.
- `rollupContributions(tx, baseCurrency)` → список `{docId, increments}`: див. нижче; планова `[]`.
- `allocatePeriod(total, from, to)` → суми по місяцях.
- `diffEffects(old, new)` не потрібен: оновлення це `−contributions(old) + contributions(new)`, створення `+new`, видалення `−old`. Одне правило, яке перевіряють property-тести.

### Rollups (`organizations/{org}/rollups/{id}`)

| id | Зміст | Вісь |
|---|---|---|
| `cash_{accountId}_{YYYY-MM-DD}` | `inMinor`, `outMinor`, `transferInMinor`, `transferOutMinor`, `inBase`, `outBase` | дата платежу |
| `cashcat_{YYYY-MM}` | `categories.{id\|_none}.{incomeBase, expenseBase}` | місяць дати платежу |
| `pl_{YYYY-MM}` | `categories.{id\|_none}.{incomeBase, expenseBase}` | місяць дати визнання (період розкладений) |

Записи це `set(..., {merge:true})` з `FieldValue.increment`, читати rollups під час запису не потрібно. Операція зі скасуванням дає від'ємні прирости. Якщо рахунок у базовій валюті, `inBase = inMinor`.

Одна операція торкається не більше: 2 рахунків, 2 `cash`, 2 `cashcat`, до 36 `pl`, ще стільки ж для старої версії при PATCH, операції, аудиту, замка. Це далеко нижче ліміту 500 записів транзакції Firestore.

### Аудит (`organizations/{org}/audit/{autoId}`)

`{ at, uid, action, targetId, before, after }`; `action` ∈ `tx.create`, `tx.update`, `tx.delete`, `account.create`, `account.update`, `account.delete`, `org.update`, `ledger.rebuild`, `migration.v2`. `before`/`after` це знімки документа (дати рядками). Читає власник, пише лише сервер.

## Інтерфейс

### Модулі

- `lib/domain/ledger/`: типи, `money.ts` (перетворення major↔minor, округлення), `days.ts` (дні `YYYY-MM-DD`, можна взяти `lib/server/fx/days.ts` як джерело й перенести в domain, S04 імпортує звідти), `period.ts`, `effects.ts`, `validate.ts`.
- `lib/server/ledger/`: `store.ts` (зв'язок з Firestore через інʼєктований `Firestore`), `write.ts` (`createTransaction`, `updateTransaction`, `deleteTransaction`, `createAccount`, `updateAccount`, `deleteAccount`), `verify.ts` (`verifyLedger`), `rebuild.ts` (`rebuildLedger`), `audit.ts`, `lock.ts`, `index.ts` (єдиний модуль із `import 'server-only'`, будує екземпляр над `getAdmin().db`, як `lib/server/fx/index.ts`).
- `lib/api/ledger-client.ts`: `fetch`-обгортки з тими самими сигнатурами, що мали клієнтські функції; `lib/firebase/transactions.ts` і `accounts.ts` лишають лише читання та мапер v2 → UI-тип.
- `Transaction` (UI-тип) отримує `status`, `accrual`, `toAccountId`, `toAmount`; `date` це `paymentDate` як `Date` (UTC-північ). `counterpartyId` для переказу більше не використовується; `TransactionForm` переходить на `toAccountId`. Форма операції більше не має вибору валюти (береться валюта рахунку) і для переказу між різними валютами просить другу суму. Журнал операцій показує лише `actual`. У списку операцій в інтерфейсі ще немає кнопки видалення (видалення є в API й у клієнті `lib/api/ledger-client.ts`).

### Роути

Усі: `requireOrgRole(['owner','accountant'])`, перевірка `Origin`, суворий парсинг тіла, `FxError` і `LedgerError` відображаються на 400/404/409/422/503 без сирого тексту.

- `POST /api/orgs/{orgId}/transactions` → 201 `{ transaction }` (або 200 з наявною при повторі `clientId`)
- `PATCH /api/orgs/{orgId}/transactions/{txId}` → 200 `{ transaction }`
- `DELETE /api/orgs/{orgId}/transactions/{txId}` → 204
- `POST /api/orgs/{orgId}/accounts`, `PATCH`/`DELETE …/accounts/{accountId}`
- `PATCH /api/orgs/{orgId}` (лише owner): назва, валюта (із заморожуванням)
- `POST /api/orgs/{orgId}/ledger/rebuild?apply=0|1` (лише owner): dry-run повертає лічильники й перші розбіжності; `apply=1` перебудовує підсумки та баланси і пише `ledger.rebuild`

### Правила Firestore

`accounts`, `transactions`: лише `read` (owner/accountant/viewer). Додаються `rollups` (читання owner/accountant/viewer) і `audit` (читання owner); запису з клієнта немає. `ledger/**` закрито. Браузер більше не оновлює документ компанії взагалі: `update` для `organizations/{id}` закрито, назва й валюта змінюються через `PATCH /api/orgs/{orgId}`. Коментар у шапці правил оновлено.

## Міграція (`scripts/migrate-ledger-v2.ts`, запуск `npx tsx`)

Запуск: `npm run migrate:ledger` (dry-run) з прапорцями `--apply`, `--drop-legacy`, `--reset-opening=<id,id>`, `--org=<id>`. Як `migrate-memberships.mjs`: за замовчуванням dry-run, ідемпотентна, захист від випадкового запуску на проді (`--project=finflow-e94b5`; `--drop-legacy` додатково потребує `--rules-deployed`), виводить лише лічильники й ідентифікатори. Аргументи перевіряє `scripts/lib/migrate-ledger-args.ts`: невідомий прапорець завершує скрипт з кодом 2, `--apply` і `--drop-legacy` не поєднуються в одному запуску. Не запускайте дві міграції одночасно.

Резервна копія: один файл на компанію, `.secrets/ledger-v2-backup-<ISO-час із ':' → '-'>-<orgId>.json`, пишеться перед змінами цієї компанії; якщо запис копії не вдався, компанію не чіпають.

Маркер міграції на документах: `migratedFrom: 'v1'`.

Для кожної компанії:
1. Операції: `date` (Timestamp, доба UTC) → `paymentDate` і `accrual.date`; `amount` → `amountMinor` (округлення до 2 знаків, невалідні суми й дати зараховуються в `skipped` з причиною); `type` лишається; переказ: `counterpartyId` → `toAccountId`, `toAmountMinor = amountMinor` (старі дані не мали другої суми; для переказу між різними валютами це лічиться у звіті окремо), `toCurrency` береться з рахунку призначення; `status: 'actual'` (операції з датою після сьогодні теж лишаються `actual`); якщо `currency` старої операції відрізнялась від валюти рахунку, операція зберігає валюту рахунку, а стару кладе в `legacy.currency`; для не-базової валюти операція отримує знімки `resolveRate`; `schemaVersion: 2`. Застарілі поля `categoryId`, `description`, `projectId`, `counterpartyId` зі значенням `null` або не рядком видаляються під час міграції.
2. Рахунки: `openingMinor = legacy balance − Σ операцій` (у minor), `balanceMinor = legacy balance`, тож видимі баланси не змінюються, якщо не вказано `--reset-opening=<ids>` (ці рахунки відкриваються з 0, а баланс стає сумою операцій). Різниця «було в `balance` проти суми операцій» друкується для кожного рахунку (сюди потрапляє випадок із скріншота), і лише після вашого «ок» на dry-run застосовується.
3. Rollups будуються `rebuildLedger` (той самий код, що й для API).
4. Пишеться запис аудиту `migration.v2`.
5. Нові поля пишуться **додатково**, старі (`date`, `amount`, `balance`) лишаються до окремого кроку очищення `--drop-legacy` (після розгортання). Він відмовляє для компанії, у якої є невалідний документ старої схеми або `verifyLedger` показує розбіжності.

### Порядок розгортання

1. `firebase deploy --only firestore:indexes --project finflow-e94b5 --account "$FIREBASE_ACCOUNT"` і чекати, поки три індекси за `paymentDate` стануть READY (перевірити запитом) до мерджа; це урок S02;
2. dry-run, перегляд розбіжностей разом із власником;
3. `--apply` (старий код ігнорує нові поля, продакшн працює);
4. merge, Vercel, `firebase deploy --only firestore:rules` (рядки правил із закритим записом активні одночасно з новим кодом);
5. повторний `--apply` (ловить операції, створені старим кодом між кроками 3 і 4);
6. `POST …/ledger/rebuild?apply=0` на кожній компанії: розбіжностей немає;
7. після перевірки власником `--drop-legacy`.

Між кроками 4 і 5 старий код, що ще лишився у відкритих вкладках, не зможе записати (правила закриті), це очікувана поведінка.

## Тестування

- **Property-тести домену** (випадкові цикли, як у S04, без нової залежності): довільні послідовності create/update/delete з різними типами, статусами, датами, періодами й валютами. Інваріанти: (1) `balanceMinor == openingMinor + Σ balanceEffects(actual)`; (2) накопичені rollups == `rebuild` з нуля; (3) `Σ allocatePeriod == total`; (4) create + delete повертає всі підсумки до нуля; (5) update еквівалентний delete + create.
- **Одиничні тести**: перетворення сум, валідація (кожне правило), розкладання періоду (кінець року, лютий, один день), знімки курсу (кап до сьогодні, збіг дат), мапер v2 → UI.
- **Інтеграція на емуляторі Firestore** (Admin SDK): повні потоки write/verify/rebuild, замок і `ledger_busy`, ідемпотентність `clientId`, заморожування валюти, відмова при видаленні рахунку з операціями, ролі (viewer 403).
- **Rules-тести**: клієнт не пише `accounts`/`transactions`/`rollups`/`audit`/`ledger`, читає за ролями, не міняє `currency` компанії.
- **Тест роутів** (як `rates.test.ts`): 401, 403, 400, 404, 409, 200/201/204.
- **Тест міграції**: фікстура зі старої схеми (включно з випадком 1234,50 проти 1234,60, переказом через `counterpartyId`, невалідними документами) → очікувані документи; ідемпотентність (другий запуск без змін); dry-run нічого не пише.
- **E2E (Playwright на емуляторах)**: сценарій зі скріншота: створити рахунок, додати операції, змінити суму, змінити рахунок, видалити; баланс щоразу дорівнює сумі; перекази PLN→PLN. Перевірка в UI, що форма й журнал працюють без видимих змін.
- Не охоплено: жива перевірка на проді з реальним НБП (перша авторизована перевірка `/api/rates` теж ще не виконана), реальний банк (S09).

- Банківський ingest і дедуплікація за зовнішнім id: S09 (дедуплікація стане на `clientId`/окреме поле).
- Масове створення (імпорт файлів): S14 (потрібен пакетний режим запису, що дотримується ліміту 500 записів на транзакцію).
- Права на рівні окремих рахунків, періоди закриття: пізніше.

## Відомі наступні кроки (follow-ups)

- **Гаряча точка запису.** `cash_*`, `pl_*` і замок отримують запис від кожної операції компанії; Firestore тримає приблизно 1 запис/с на документ. Достатньо для малого бізнесу; для банківського ingest (S09) і імпорту (S14) писати пакетами по декілька операцій на транзакцію.
- **Вартість індексів.** `pl_*` і `cashcat_*` це документи з картою категорій; вкладені індекси можна вимкнути виключенням (як для `fxTables`).
- **Другий знімок для переказу PLN→EUR.** Базові суми переказів не зберігаються; S12 вирішує, чи рахувати курсову різницю з них.
- **Зміна дат у минулому закритого періоду.** Закриття періоду не входить, S05 дозволяє редагувати будь-яку дату (запис в аудиті).
