# S04 — Курси НБП: `resolveRate`, кеш таблиць у Firestore

> Статус: **реалізовано в гілці `s04-nbp-rates`, чекає мерджа.** Дизайн затверджено користувачем 2026-10-26. Для однакових валют (`from === to`) `source` дорівнює `'identity'` (курс 1, без звернення до НБП), інакше `'NBP_A'`.

## Мета

Дати застосунку відтворюваний курс валют для перерахунку в PLN за польським податковим правилом. Це серверний будівельний блок для S05 (запис операції зберігає знімок курсу), S07 (форма операції підставляє курс) і S12 (курсові різниці). Екрана в S04 немає.

## Вихідний стан (перевірено)

- Курсів у коді немає. Валюти застосунку: PLN, EUR, USD, UAH (`lib/utils`, правила Firestore).
- Roadmap (`2026-10-22-finflow-roadmap.md`): курс NBP таблиці A знімається при першому записі; правило попереднього робочого дня; без cron, ліниві курси та кеш у Firestore.
- Перевірено запитом до `https://api.nbp.pl/api/exchangerates/tables/A/{from}/{to}/?format=json` (2026-10-26):
  - відповідь: масив `{table, no, effectiveDate, rates[{currency, code, mid}]}`; 32 валюти, UAH і EUR є;
  - діапазон до 93 днів, довший дає 400; діапазон у майбутньому дає 400; минулий діапазон без таблиць дає 404;
  - вихідні й свята не мають таблиць (у жовтні 2026: 18 таблиць за 18 робочих днів).

## Рішення

| Питання | Рішення |
|---|---|
| Політика курсу | Одна, без налаштувань: таблиця A з найбільшою `effectiveDate` **строго меншою** за дату операції. Понеділок бере п'ятницю, свято бере останню опубліковану таблицю, майбутня дата бере останню опубліковану. Календар свят не потрібен: дні без таблиць відсіюються самі. |
| Параметр `policy` | Немає (YAGNI). Сигнатура `resolveRate(from, to, date)`. Відхилення від roadmap, де згадано `policy`. |
| Ручні курси, «на дату», таблиця B, інші провайдери | Поза S04. |
| Результат | Знімок для зберігання в операції (S05): `{ rate, from, to, requestedDate, rateDate, tableNo, source: 'NBP_A', final }`. |
| `final` | `true`, коли `date <= сьогодні` (усі таблиці до цієї дати вже опубліковані, знімок не зміниться); `false` для пізнішої дати (до неї може з'явитися нова таблиця). Знімок для однакових валют завжди `final: true`. S05 зберігає назавжди лише `final: true`; нефінальний знімок перераховується при першому збереженні після настання дати. |
| Точність | `rate` округлюється до 8 знаків (як у Finmap). |
| Кеш | Firestore, колекція `fxTables`, один документ на місяць. |

## Модель

### Дати

Усі дати в S04 це рядки `YYYY-MM-DD` (доба UTC, як і дати операцій у застосунку). «Сьогодні» для оновлення кешу береться з `todayUtcDay()` (варшавська дата).

### Формули

`mid(X)` це PLN за одну одиницю X з таблиці A на `rateDate`.

- `from == to`: `rate = 1`, до НБП не звертаємось, `rateDate = requestedDate`, `tableNo = null`.
- `X → PLN`: `mid(X)`.
- `PLN → X`: `1 / mid(X)`.
- `X → Y`: `mid(X) / mid(Y)`.

Результат округлюється до 8 знаків. Обидві валюти беруться з однієї й тієї самої таблиці.

### Пошук таблиці для дати D

1. Цільовий момент: найбільша `effectiveDate < D`.
2. Беремо місячний документ для місяця `D - 1 день`; якщо в ньому немає таблиці раніше D (наприклад, на початку місяця), беремо попередній місяць, і так до 2002-01 (перша таблиця A: 2002-01-02). Якщо таблицю не знайдено (дата до 2002 року теж): помилка `no_rate_before`, 404.
3. Верхня межа дати: `сьогодні + 366 днів`, далі `invalid_params`.

### Кеш `fxTables/{YYYY-MM}`

Документ: `{ month, tables: [{ no, effectiveDate, rates: { EUR: 4.4026, … } }], fetchedAt, fetchedDay, complete }`. `fetchedDay` це варшавська доба завантаження (`YYYY-MM-DD`, `deps.today()` на момент запиту); `parseMonthDoc` без коректного `fetchedDay` вважає документ промахом кешу.

- Місяць, який уже закінчився до сьогоднішньої варшавської дати, після завантаження позначається `complete: true` і не оновлюється ніколи.
- Поточний місяць: `complete: false`. Кешований місяць відповідає на дату D без НБП, якщо він `complete`, **або** `fetchedDay >= D` (кожна таблиця до D опублікована ще до кінця доби завантаження), **або** `now - fetchedAt < 1 год`. Інакше він оновлюється.
- Завантаження: один запит НБП на межі місяця (до 31 дня, у межах ліміту 93). Відповідь 404 для минулого місяця без таблиць дає порожній `tables`.
- **Перевірка оновленого місяця** (`validateRefresh` у `rates.ts`, чиста функція) перед записом: (а) кожна `effectiveDate` із кешованого документа є й у новій відповіді; (б) завершений місяць не порожній; (в) номери таблиць `N/A/NBP/YYYY` в межах одного року йдуть підряд без пропусків (нерозбірливий `no` ігнорується). Будь-яке порушення дає `provider_unavailable`, нічого не записується, далі діє запасний варіант нижче. Так гірша відповідь НБП ніколи не замінює добрий кеш.
- Якщо оновити не вдалося (НБП недоступний, сміття, провалена перевірка), застарілий документ використовується, лише коли `fetchedDay >= D` або в ньому є таблиця з `effectiveDate >= D`: тоді результат гарантовано правильний. Інакше помилка `provider_unavailable`. На проміжку між місяцями (обхід назад) недоступний НБП для некешованого попереднього місяця дає `provider_unavailable`.
- Помилка читання кешу (`store.get`) це промах кешу (лог `fx cache read failed`), не 500. Помилка запису кешу лише логується.
- Запис кешу ідемпотентний (`set` повного документа).
- **Кеші в пам'яті** (у `createResolver`; `resolveRate` будує резолвер один раз на процес): мапа завершених місяців (вони не змінюються); мапа оновлень «у польоті» (одночасні запити одного місяця діляться одним запитом до НБП і одним `store.set`); **пам'ять про збій**: після невдалого оновлення місяця НБП для цього місяця не викликається 30 секунд (одразу запасний варіант або `provider_unavailable`).

### Правила Firestore

Колекція `fxTables` закрита для клієнтів (читання й запис заборонені). Читає й пише лише сервер через Admin SDK. Явного `match` не потрібно, але rules-тест доводить відмову.

## Інтерфейс

### Модулі (`lib/server/fx/`, лише сервер)

- `nbp.ts`: клієнт НБП (`fetchNbpTables(fromDay, toDay)`, таймаут, перевірка форми відповіді: `table === 'A'`, `effectiveDate` у межах діапазону, без дублікатів, коди помилок).
- `store.ts`: читання й запис `fxTables` через Admin SDK, `parseMonthDoc`.
- `rates.ts`: чиста логіка вибору таблиці, формул і перевірки оновлення (`pickTable`, `crossRate`, `round8`, `validateRefresh`), без I/O.
- `resolver.ts`: `createResolver(deps)`: політика кешу, обхід місяців, кеші в пам'яті, пам'ять про збій.
- `days.ts`: робота з днями `YYYY-MM-DD`.
- `index.ts`: `resolveRate(from, to, date)`, що ліниво будує один резолвер на процес із Firestore-сховищем і клієнтом НБП.
- `import 'server-only'` на модулях з I/O (діє правило `check:server-imports`).

### Роут `GET /api/rates?from=EUR&to=PLN&date=2026-10-26`

- Потрібна сесія (`requireUser`); компанія не потрібна, курси публічні.
- Валідація: `from`, `to` 3 великі латинські літери, `date` дійсна `YYYY-MM-DD`, зайві параметри 400. Дата пізніша за `сьогодні + 366 днів` це `invalid_params` (400); дата до 2002 року це `no_rate_before` (404).
- 200 `{ rate, from, to, requestedDate, rateDate, tableNo, source, final }`, `Cache-Control: private, max-age=300`.
- 400 `invalid_params`; 404 `unsupported_currency` (код не в таблиці A) або `no_rate_before`; 503 `provider_unavailable`. Помилка НБП не віддає клієнту сирого тексту.

### Підтримувані валюти

Будь-яка, що є в таблиці A на потрібну дату (PLN синтетична, `mid = 1`). Список валют застосунку не обмежується в S04.

## Тестування

- Unit на фікстурах реальних відповідей НБП (зберігаємо уривки в `tests/fixtures/nbp/`): понеділок бере п'ятницю; 1 листопада (неділя) і 11 листопада (свято) бере останню таблицю; Різдво; Великдень; 1-ше число місяця (перехід місяця й року); майбутня дата; дата раніше 2002; невідома валюта.
- Property-тести (`fast-check` або власні випадкові цикли): `A→B × B→A ≈ 1` (з урахуванням округлення 8 знаків), `A→C ≈ A→B × B→C`, результат монотонний за вибором таблиці.
- Кеш: промах, влучання, завершений місяць не оновлюється, поточний оновлюється після години лише для дати пізнішої за `fetchedDay`, відмова НБП при застарілому кеші (обидві гілки, перехід через межу місяця), збій читання кешу, `validateRefresh` (втрата дня, порожня відповідь, пропуск номера), `final`, одночасні запити (один виклик НБП і один `set`), пам'ять про збій (30 с), узгодженість годинника (сьогоднішня таблиця ще не опублікована).
- Wiring-тест `index.test.ts`: `resolveRate` над in-memory Admin-базою й `fetch`, що віддає записані фікстури; документ лягає в `fxTables/2026-10`, другий виклик не звертається до `fetch`.
- Rules-тест: клієнт не читає й не пише `fxTables` (аутентифікований і ні).
- Тест роуту з підміненим `fetch` і Admin-сховищем на емуляторі: 401 без сесії, 400, 404, 503, 200.
- Ручний скрипт `scripts/check-nbp.mjs` (не в CI): реальний запит і порівняння з очікуванням для відомої дати.

## Відомі наступні кроки (follow-ups)

- **Обмеження частоти на `/api/rates` для користувача** (зараз `requireUser` лише перевіряє сесію; кеші в пам'яті й пам'ять про збій обмежують звернення до НБП, але не до самого роуту).
- **Округлення до 8 знаків губить точність для крихітних крос-курсів екзотичних валют.** Якщо S05 це знадобиться, зберігати `mid` обох валют або значущі цифри.
- **Необов'язкове виключення з індексів Firestore для `fxTables.tables`**, щоб зменшити вартість запису (документ місяця великий, індекси по вкладених полях не потрібні).
