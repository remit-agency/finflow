# FinFlow — дорожня карта до Finmap-класу (2026-10-22)

> Статус: **затверджено** (2026-10-22). Кожен підпроєкт проходить окремий цикл «спека → план → реалізація».
> Джерела: [звіт reverse-engineering Finmap](../../research/finmap-reverse-engineering.md), інвентар коду finflow, gap-аналіз (125 функцій у 4 кластерах), два незалежні плани декомпозиції (foundation-first 6.6/10, value-first 7.6/10) і синтез судді.

## Рамки

- **Продукт:** cash-flow / управлінський облік для МСБ, ринок **Польща**, інтерфейс **PL + EN + UA**, базова валюта **PLN** за замовчуванням.
- **Підхід:** розширюємо наявний код finflow (Next.js + Firebase), а не переписуємо. Копіюємо функції й UX-патерни Finmap, **не** їхній код, тексти чи ассети.
- **Дані:** у Firestore лише тестові дані, тому схему можна перебудовувати без міграцій.
- **Інфраструктура:** Vercel (team `biuro-3838s-projects`, регіон функцій `fra1`), Firestore `finflow-e94b5` у `eur3` (EU), GitHub `remit-agency/finflow`, банки через Enable Banking (AIS, PSD2).

## Ключові рішення

| Рішення | Чому |
|---|---|
| Хостинг Vercel замість Cloudflare Pages | Нативний Next.js і Node-рантайм. `firebase-admin` працює без REST-обходів, що прибирає головний технічний ризик |
| Один серверний шлях запису для обліку | Атомарний коміт операції, балансів, місячних підсумків і аудиту, без дрейфу балансів |
| Суми цілими мінорними одиницями (грош) | Без помилок float. Розподіл методом найбільшого залишку |
| Курс NBP (таблиця A) знімається при першому записі | Відтворювана конвертація в PLN. Правило попереднього робочого дня |
| Дві дати на операції (`cashDate` / `accrualDate`) | Cash Flow рахується за датою руху грошей, P&L — за датою нарахування, як у Finmap |
| Контрагент один, з ролями (`roles[]`) | Клієнт / постачальник / кредитор / позичальник / інвестор / власник / працівник / податкова |
| Без cron в MVP | Синхронізація банку при відкритті застосунку, ліниві курси NBP, розклади на 12 міс. наперед |
| Vercel Hobby для розробки, **Pro** до S17 | Hobby дозволено лише для некомерційного використання |

- **Відкладено:** див. S18–S25.

## Ризики

1. **Enable Banking:** production працює в обмеженому режимі до підписання договору; є плата за підключений рахунок; не всі польські бізнес-банки покриті. Перший тиждень S09 — spike; за потреби S14 (імпорт) іде раніше.
2. **Дрейф rollups** псує всі звіти. Чиста `computeDeltas` + property-тести + `rebuildRollups` у CI + нічна перевірка (S18).
3. **Ліміти Firestore:** 500 записів на коміт, ~1 запис/с на гарячий документ, 1 MiB на документ. Rollup-мапи тримаємо малими, бекфіл чанками.
4. **Ліміти Vercel Functions:** тривалість і пам'ять. Довгі синхронізації робимо resumable через `continuation_key`.
5. **Два стани auth** (клієнтський SDK і серверна cookie) можуть розійтись. Явна синхронізація в S01 + Playwright.
6. **RODO:** банківські дані ФОП (JDG) — це персональні дані. S15 до першого реального банку.
7. **Платежі в Польщі:** Stripe-підписки фактично лише карткові, BLIK не повторюваний. Fallback — річна передоплата переказом.
8. **Обсяг:** 18 підпроєктів MVP. Пом'якшення: бета-ворота, строгий список відкладеного, явні тригери «підтягнути раніше».
9. **Прогалини у звіті про Finmap** (життєвий цикл плану, пороги зіставлення, крайні випадки повторень, правила боргів). Кожна спека фіксує **власне** правило, що заодно знижує IP-ризик.
