# CLAUDE.md — FinFlow Project Rules

## Project Overview
**FinFlow** — SaaS cash-flow and management-accounting app for small/medium businesses (2–50 people). Target market: Poland (PL/EN/UA interface planned in S03, base currency PLN).
Working today: accounts, income/expense/transfer transactions, Cash Flow, P&L, Balance, payment calendar, CSV export, bank connection through Enable Banking with the sync and the expiry notice (S09), auto-rules that give bank operations a category and a counterparty (S10), tags that people create themselves, with «не враховувати в аналітиці» keeping an operation out of Cash Flow and P&L while the balances stay whole (S10t), and own transfers: the journal suggests bank-to-bank pairs, a bank operation becomes a transfer to a cash box, two bank operations merge into one transfer and every one splits back, the bank balances whole (S10b), and report filters: Cash Flow, P&L and the Calendar filter by payment type and category, counterparty, tag (with «без тегів») and account, the Balance by account, the choice kept in the address across the report tabs (S10f), and planned payments: series (rent, subscriptions, the ZUS, PIT-4 and VAT-7 presets) keep planned operations three months ahead, filled daily by the hourly cron call; the journal suggests plan ↔ bank pairs confirmed in one click without a duplicate, and «Прострочено» marks the planned operations whose day passed; planned operations never move balances or reports (S11), and server reports: Cash Flow, P&L and the balances are computed on the server (from the rollups without filters over whole months, else from the operations of the period, within 10 000 documents), with the month-end reconciliation (opening, net movement, excluded from analytics, outside the filter, transfers, exchange difference, closing, «Розбіжність»), CSV and XLSX export of the same response, and the Balance page on the same server balances (S12). The dashboard «Гроші зараз» was removed on 2026-11-11 (owner: not needed).
Roadmap: `docs/superpowers/specs/2026-10-22-finflow-roadmap.md`. Sub-project specs: `docs/superpowers/specs/`, plans: `docs/superpowers/plans/`, change log and known follow-ups: `PROGRESS.md`.

## Tech Stack
- **Framework:** Next.js 16 (App Router; Turbopack for `next dev` and `next build`), React 19.2, TypeScript 5 (strict)
- **Proxy:** `proxy.ts` — the Next 16 name for middleware (Node.js runtime). It gates only app pages (`/<segment>/...`, see `isAppPath` in `lib/auth/paths.ts`): it verifies the signature and expiry of the `__session` cookie (not revocation); an invalid cookie is cleared and the visitor is redirected to `/login?redirect=…`, a verification failure on our side (including Google signing-key fetch errors) answers 503 and leaves the cookie alone. `/login` and `/register` are never redirected, so a visitor with a stale cookie can always sign in again. Firestore data is protected by security rules, not by the proxy.
- **Auth/session (S01):** after every Firebase sign-in the browser calls `POST /api/auth/session` with a fresh ID token (`auth_time` ≤ 5 min, else 401 `reauth_required`); the server mints an HttpOnly 7-day Firebase session cookie (`__session`). Sessions are absolute: there is no silent renewal. API routes call `await requireUser(req)` / `requireVerifiedUser(req)` from `lib/server/auth.ts` (revocation-checked; POST/PUT/PATCH/DELETE also need a same-origin `Origin`; `requireVerifiedUser` reads the live user record, not the cookie claim). There is no Bearer-token auth. Every route under `app/api` must call one of them or be on the allow-list (with a reason) in `tests/unit/server/route-auth-coverage.test.ts`. Sign-out calls `POST /api/auth/logout`, which revokes ALL refresh tokens of the user (every device is signed out), but only through a live, non-revoked session (a stale revoked cookie is merely cleared); the root `AuthProvider` triggers it too when the SDK has no user. The Banks settings page (`settings/banks`, where the Enable Banking callback returns) reads only the flags `?eb_connected=1` and `?eb_error=1`: the callback saves the bank session on the server (`saveSession` in `lib/server/banking/link.ts`), so the redirect carries no session id; members do see it as the connection id in `GET /api/orgs/{orgId}/bank` (a non-secret handle: using it needs the app's private key), and a legacy `?eb_auth=` link does nothing (S09 removed the browser-side `eb_pending` flow). Never write `__session` from client code. Shared path and `?redirect=` rules (`safeRedirectPath`) live in `lib/auth/paths.ts`.
- **Client data:** Firebase JS SDK 12 (Auth + Firestore), used only from `lib/firebase/` and `lib/hooks/`
- **Server data:** `firebase-admin`, used ONLY inside `lib/server/` (each file starts with `import 'server-only'`); entry point `getAdmin()` in `lib/server/firebase-admin.ts`. Firestore uses `preferRest: true` in production only (faster serverless cold start); on the emulator it uses gRPC, because REST would need Application Default Credentials
- **UI:** shadcn/ui (`base-nova` style on `@base-ui/react`), Recharts, Tailwind CSS 4, lucide-react, next-themes, sonner
- **Banking:** Enable Banking (AIS/PSD2) — connection routes `app/api/enablebanking/{institutions,session,callback}`, bank routes `app/api/orgs/[orgId]/bank/**`, the server module `lib/server/banking/` (behind the `EbApi` interface), `lib/enablebanking/jwt.ts` (server-only JWT), `lib/enablebanking/client.ts` (`ebFetch` for the bank picker: same-origin fetch that authenticates with the session cookie; on 401 it clears the session and navigates to `/login?redirect=…`)
- **Payments:** Stripe is NOT wired yet (`lib/stripe.ts` is unused; billing arrives in S17)
- **Tooling:** npm, Node.js 24 (`engines.node` = `24.x`), ESLint 9 flat config (`eslint.config.mjs` + `eslint-config-next` 16), Vitest, `@firebase/rules-unit-testing`, Playwright

## Firestore Data Model (S00, S02)
- `organizations/{orgId}`: `{ name, currency, ownerId, plan, trialEndsAt, createdAt }` (no `members` map since S02; `ownerId` is informational, access is decided by the membership document)
  - `members/{uid}`: `{ uid, role: 'owner' | 'accountant' | 'viewer', createdAt, addedBy }` (`uid` repeats the document id: the collection-group query filters on it)
  - subcollections: `accounts`, `categories`, `transactions`, `bankConnections` (S09: written by the server only, readable by the owner), `counterparties` (S06, read-only for clients), `counterpartyKeys` (S06, server only; uniqueness keys), `bankAccounts` and `bankSeen` (S09, server only: the linked bank accounts with their sync state, and one mark per imported bank operation), `rules` (S10, written by the server, readable by every member), `tags` (S10t, written by the server, readable by every member), `tagKeys` (S10t, server only; name keys), `recurring` (S11, written by the server, readable by every member), `recurringDone` (S11, server only; one mark per paid, skipped or deleted occurrence)
- `_meta/{docId}` — server-only (for example `_meta/health`); clients are denied by the rules
- Membership lookup on the client (`lib/firebase/members.ts`): `getMemberships(uid)` is a collection-group query `collectionGroup('members').where('uid', '==', uid)` (the rules are not a filter, so the query must constrain `uid` to the caller's own uid); `getMyOrganizations(uid)` loads the organizations of those memberships by id (organizations cannot be listed); `getMembership(orgId, uid)` reads the caller's own member document (its role, or null = no access). The collection-group index is in `firestore.indexes.json` (`fieldOverrides` for `members.uid`).

### Roles and tenancy (S02)
| Role | Data (`accounts`, `categories`, `transactions`) | Banks (`bankConnections`, Enable Banking) | Company name/currency | Subscription page |
|---|---|---|---|---|
| `owner` | read, write | read, write | edit | yes |
| `accountant` | read, write | no | read only | no |
| `viewer` | read only | no | read only | no |

- `can(role, action)` in `lib/shell/permissions.ts` (pure, shared by browser and server; actions `data.write`, `bank.manage`, `company.edit`, `subscription.view`). The role-aware UI is a convenience; the protection is `firestore.rules` (`hasRole(orgId, roles)`) and `requireOrgRole`.
- Clients never create or delete organizations or memberships and never change `ownerId`, `plan`, `trialEndsAt` or `createdAt`; only the server writes them (`POST /api/orgs`, the migration script). An owner may update only `name` and `currency`.
- Companies are created only by `POST /api/orgs` (`lib/server/orgs.ts`): a transaction creates the organization and the owner membership together; a user may own at most 3 companies (409 `org_limit_reached`).
- The collection name `members` is reserved for memberships: the collection-group rule in `firestore.rules` applies to every collection with that name. Never use it for anything else.
- A new subcollection under `organizations/{orgId}` is closed until it is added to the lists in `firestore.rules` (read and write roles) and to the matrix in `tests/rules/firestore.rules.test.ts`.
- Migration of the legacy `members` map: `node scripts/migrate-memberships.mjs` (dry run), `--apply` (creates missing membership documents, idempotent), `--drop-members-map` (removes the legacy field, only after verification in production). With `FIRESTORE_EMULATOR_HOST` set it targets the emulator and uses no credentials. Rollout order is in the S02 spec.

## Coding Conventions
- TypeScript strict mode always
- Server Components by default, `'use client'` only when needed (forms, hooks, charts)
- Next 16: `params`, `searchParams`, `cookies()`, `headers()` are async — always `await` them (or React `use()` in client components)
- Client Firebase calls only in `/lib/firebase/` and `/lib/hooks/` (legacy exception: `app/(app)/[orgSlug]/settings/company/page.tsx` and `settings/categories/page.tsx` still call `updateDoc`/`deleteDoc` directly)
- Server-side Firestore/Auth only through `getAdmin()` from `lib/server/`; route handlers that use it `export const runtime = 'nodejs'`; map errors with `HttpError` + `errorResponse()`
- Browser → API calls that need a user rely on the `__session` cookie (`ebFetch`, same-origin); the route calls `requireUser()` / `requireVerifiedUser()` and then `requireOrgRole(uid, orgId, [...roles])` (reads `organizations/{orgId}/members/{uid}`; no membership, an unknown role or a role outside the list all give the same 403 `forbidden`; returns the role). The Enable Banking routes (`session`, `callback`) and the bank routes that link, sync or disconnect (`app/api/orgs/[orgId]/bank/{accounts,sync,connections/[connectionId]}`) use `requireOrgRole(uid, orgId, ['owner'])`; the status read `GET /api/orgs/{orgId}/bank` accepts every member (non-owners get the connections only)
- Enable Banking OAuth `state` is HMAC-signed (`lib/server/eb-state.ts`, 15 min) and carries uid + orgId; the callback verifies it, requires the session uid to equal the state uid, and re-checks the owner role. The bank connection (`/api/enablebanking/session`) needs a verified email (`requireVerifiedUser`, 403 `email_not_verified`); verification is soft everywhere else
- `cn()` from `lib/utils` for className merging
- All dates: `Date` objects in code, Firestore `Timestamp` in DB
- Money, numbers, dates: never call `toLocaleString`/`toLocaleDateString` or hard-code `'uk-UA'`; use `useFormatters()` in components and `lib/i18n/format.ts` elsewhere (see "i18n (S03)")
- Before committing: `npm run lint && npm run typecheck && npm run test:unit` (add `npm run check:server-imports` when you touch server dependencies)

## i18n (S03)
- **Languages:** `pl` (default), `en`, `uk`; `next-intl` 4 without i18n routing, so URLs carry no language prefix. `lib/i18n/config.ts` has `LOCALES`, `DEFAULT_LOCALE`, `LOCALE_COOKIE` (`NEXT_LOCALE`), `INTL_LOCALE` (BCP 47 tag per language), `LOCALE_LABELS` (each language in its own name), `isLocale`.
- **Resolution order** (`i18n/request.ts` + `lib/i18n/negotiate.ts` `resolveLocale`): a valid `NEXT_LOCALE` cookie, else `Accept-Language` (by `q`, primary subtag only), else `pl`. The cookie value is validated with `isLocale` and never echoed into HTML or headers. `<html lang>` follows the locale, so the root layout is dynamic (marketing pages lose the static cache until S17). The time zone for formatting is `Europe/Warsaw`.
- **Catalogs:** `messages/{uk,pl,en}.json`, nested by zone (`common`, `auth`, `shell`, `roles`, `journal`, `forms`, `settings`, `analytics`, `charts`, `periods`, `errors`, ...). Typed from `messages/uk.json` (`global.d.ts`), so a missing key fails `typecheck`. `tests/unit/i18n/catalogs.test.ts` requires the same keys and the same ICU argument names in all three. Components: `useTranslations('zone')` (client) or `await getTranslations('zone')` (server, `generateMetadata`). `lib/**` must not import next-intl: constants become slugs (the component calls `t(\`zone.${slug}\`)`) or the function takes `t`/`locale`.
- **String migration recipe (short):** the Ukrainian catalog keeps the exact current Ukrainian text; add the same key to `pl` and `en` with the agreed terminology (Wpływ/Wydatek/Przelew, Płatności/Analityka, Konto/Konta, Firma, Kontrahent ...); ICU plurals for counts (Polish needs `one/few/many/other`, English `one/other`); `aria-label`, `placeholder`, `title`, toasts, `confirm()` and sr-only text are strings too; user data (account and category names), brand names, currency codes and test ids are not translated. Done when `grep -nE "[А-Яа-яІіЇїЄєҐґ]" <file>` shows comments only.
- **Formats:** `useFormatters()` (`lib/i18n/useFormatters.ts`) binds the active locale; the pure helpers are in `lib/i18n/format.ts` (`formatMoney`, `splitMoney`, `currencySymbol`, `formatNumber`, `formatDate`, `formatWeekday`, all take a `Locale`). Note: pl-PL (CLDR) starts digit grouping at 5 digits, so `1234,50` has no separator but `12 345,50` does.
- **Amount input:** `parseAmountInput(text)` (`lib/utils/amount-input.ts`) accepts `1 234,50`, `1234.5`, `1.234,50`, `1,234.50` and returns `number | null`; every amount field parses through it and the stored value is a plain number.
- **Polish calendar:** `lib/utils/pl-calendar.ts` (`easterSunday`, `polishHolidays(year)`, `isBusinessDay`, `previousBusinessDay`, `nextBusinessDay`, `addBusinessDays`) works on UTC calendar days (`Date` at 00:00 UTC); S04 (NBP rates), S11 and S13 use it. `todayUtcDay()` (`lib/utils/today.ts`) is the Warsaw date as a UTC day: pass it wherever the code needs "today"; stored days and report ranges stay UTC days (full Europe/Warsaw periods arrive in S05/S09).
- **Switcher:** `components/i18n/LanguageSwitcher.tsx`, variant `menu` (profile menu, `data-testid="language-option-<locale>"`) and `select` (auth pages, `data-testid="language-switcher"`). It writes the cookie (`lib/i18n/client.ts`) and calls `router.refresh()`; the route does not change.

## Exchange rates (S04)
- Rates come from `resolveRate(from, to, date)` in `lib/server/fx` (server only, `import 'server-only'`). The rule is one and has no settings: the NBP table A with the greatest `effectiveDate` strictly before `date` (`YYYY-MM-DD`, UTC day), so Monday takes Friday and a holiday or a future date takes the last published table. Identical currencies return rate 1 with `source: 'identity'`. S12 values a balance at the close of day D with `resolveRate(currency, base, D + 1)`, i.e. the last table published on D or before (the reconciliation and the balances); movements keep the rule of their day.
- Store the returned snapshot (`rate`, `from`, `to`, `requestedDate`, `rateDate`, `tableNo`, `source`) with the amount; never recompute a stored rate. `rate` is rounded to 8 places. Persist only `final: true` snapshots (`date <= today`: every table before it is published). A `final: false` snapshot (a date after today) can still change: S05 must re-resolve it on the first save after that date and never store it for good.
- `resolveRate` builds one resolver per process: finished months stay in memory, concurrent refreshes of a month share one NBP call, and a failed refresh is not retried for 30 s. A refreshed month is validated (`validateRefresh`) so a worse NBP reply never replaces a good cached document; cached months carry `fetchedDay` (Warsaw day of the fetch).
- Clients get rates only through `GET /api/rates?from=&to=&date=` (session required); they never read Firestore for rates. Tables are cached per month in `fxTables`, which is server-only (explicit deny in `firestore.rules`).
- Tests use recorded months in `tests/fixtures/nbp/` (`scripts/record-nbp-fixtures.mjs`); CI never calls NBP. `node scripts/check-nbp.mjs` is the manual live check.

## Ledger (S05)
- **Split:** `lib/domain/ledger/` is pure (no Firebase, no `server-only`, no `next`): minor-unit money, input parsing, validation, `balanceEffects`, rollup contributions, period allocation, `changeSet`, the expected-ledger oracle. `lib/server/ledger/` runs Firestore Admin transactions (`write.ts`, `verify.ts`, `rebuild.ts`, `lock.ts`, `audit.ts`); `index.ts` is the only module with `import 'server-only'`. The browser reads through `lib/firebase/{accounts,transactions}.ts` (v2 mapper only) and writes through `lib/api/ledger-client.ts` (`fetch` to the routes under `app/api/orgs/[orgId]/`).
- **Write rule:** every change to `accounts`, `transactions`, `rollups` and `audit` goes through `lib/server/ledger` in ONE Firestore transaction (document + account balances + rollup increments + audit). Never write those collections from the browser (Firestore rules forbid it) or from a script except through those functions. Spec: `docs/superpowers/specs/2026-10-27-s05-accounting-engine-design.md`.
- **`changeSet` is the single rule:** create applies `+new`, delete applies `-prior`, update applies both (`-prior +new`). Balance deltas and rollup increments come from it only; property tests check it against the oracle.
- **Money and dates:** integer minor units (`...Minor`, 1/100); convert only at the boundary with `toMinor` / `fromMinor`. Dates are `YYYY-MM-DD` strings (UTC day, Warsaw "today" supplied by the caller). The accrual snapshot date is capped at today, so stored FX snapshots are always `final`.
- **Invariant and repair:** `balanceMinor = openingMinor + sum of actual operations`. `verifyLedger` (read only) reports drift; `rebuildLedger` rewrites rollups and balances under the ledger lock (`organizations/{org}/ledger/lock`, a 5 minute lease; writes meanwhile get 409 `ledger_busy`). The lock is owned by a token: `acquireLock` returns it, and `renewLock` / `releaseLock` act only while the stored holder is that token (a lease taken over after expiry is never released or extended by its old holder). `rebuildLedger` renews before every batch and aborts when the lease is lost; the migration holds the lock for the whole apply, so a second run on the same company gets `ledger_busy`. Owner endpoint: `POST /api/orgs/{org}/ledger/rebuild?apply=0|1` (0 = dry run).
- **Currency freeze:** the company currency cannot change once the company has operations (409 `currency_locked`); name and currency go through `PATCH /api/orgs/{orgId}` only. An account that has operations cannot be deleted or change currency.
- **Tests:** `npx vitest run --config vitest.config.ts` (unit and property tests), `npm run test:rules`, `npm run test:integration` (Admin SDK against the Firestore emulator; needs Java 21, prefix `PATH="$HOME/.jre/temurin-21/bin:$PATH"`), e2e as in `.github/workflows/ci.yml`.
- **Migration:** `npm run migrate:ledger` (dry run by default; `-- --apply`, `--drop-legacy`, `--reset-opening=<ids>`, `--org=<id>`; arguments are validated by `scripts/lib/migrate-ledger-args.ts`, unknown flags exit 2). Production needs `--project=finflow-e94b5`; `--drop-legacy` also needs `--rules-deployed` and refuses a company with an invalid legacy document or a failing `verifyLedger`. One backup file per company: `.secrets/ledger-v2-backup-<ISO with : as ->-<orgId>.json`. Legacy `null`/non-string `categoryId`, `description`, `projectId`, `counterpartyId` are deleted. Do not run two migrations at once.

## Counterparties (S06)
- **Split:** `lib/domain/counterparties/` is pure (name/NIP/NRB normalisation and checksums, input parsing, document mapping, uniqueness keys, white list response parsing, search); `lib/server/counterparties/` writes. Every change to `counterparties` and `counterpartyKeys` goes through it in ONE Admin transaction (document + key documents + audit). The browser only reads `counterparties`; the rules close all client writes and all access to `counterpartyKeys` and the root `rateLimits`.
- **Uniqueness:** `counterpartyKeys/nip_{10 digits}` and `counterpartyKeys/name_{normalised name}` are created in the same transaction as the counterparty; an existing key is a `409 duplicate` with `field` and `existingId`. The name key is `name_` + lower-case letters/digits with every other run of characters replaced by one `_` (no `encodeURIComponent`); it drops Latin diacritics (`ł` is `l`) and stray combining marks such as a stress mark, while Cyrillic letters keep their identity (`й` is not `и`). `0000000000` is not a valid NIP.
- **White list (MF):** `lookupNip` (server only, `WL_API_BASE` overrides the host in tests, 8 s timeout, one retry after a network error or a timeout). An IBAN missing from the list of a company with `hasVirtualAccounts` is marked `onWhitelist: null` (not checked), not `false`. A failure is `502 lookup_unavailable` and never blocks saving: the counterparty is saved with no VAT status and `onWhitelist: null`. `vat` and `onWhitelist` are set by the server, never accepted from the client. Every white list call (the lookup route, create and update) counts against the per-user limit (`lib/server/rate-limit-guard.ts`: 30 per minute, 300 per hour); `/api/rates` shares the mechanism. Create checks the keys before asking MF, so a duplicate costs no call.
- **System records:** `system_zus` and `system_us` (`kind: 'zus' | 'us'`) are created with every new company (without audit entries) and added to existing ones by `npm run seed:counterparties` (dry run by default; `-- --apply --project=finflow-e94b5`; idempotent, found by id). They are ordinary records: editable and archivable, never deletable (there is no delete at all, only `archived`).
- **Operations:** the ledger write path checks a new `counterpartyId` in the same transaction: unknown is `422 counterparty_not_found`, archived is `422 counterparty_archived`; an edit that leaves the counterparty as it was is not re-checked.
- **UI:** settings section «Контрагенти» (`app/(app)/[orgSlug]/settings/counterparties`) and `components/counterparties/CounterpartyPicker.tsx` (controlled combobox; mounted in the operation form by S07).
- **Tests:** unit under `tests/unit/{domain,server,api}/counterparties/`, integration `tests/integration/counterparties-*.test.ts` and `rate-limit.test.ts` (Firestore emulator), rules in `tests/rules/`, e2e `tests/e2e/counterparties.spec.ts` (the dev server talks to `tests/e2e/helpers/wl-stub.mjs`, never to the real white list).

## Transaction form (S07)
- **Split:** `lib/domain/transaction-form/` is pure (`status.ts` future payment date forces `planned`, `accrual.ts` date or period state with validation, `rate.ts` implied transfer rate and PLN hint, `state.ts` `FormState`, initial state, `validateState`, `isDirty`). The bridge to the API is `lib/api/transaction-draft.ts`: `stateToDraft`, `buildEditDraft` (carries only project, tags and files; the form owns everything else, accrual, counterparty and status included) and `transactionToDraft` (the full draft of a stored operation, for undo). The server was not changed.
- **Form:** `components/forms/transaction/` (`TransactionForm` holds the state; `StatusField`, `AmountFields`, `DatesFields`, `CounterpartyField`, `ConfirmDialog`); `components/forms/TransactionForm.tsx` is a re-export for the lazy loader. Fields are rendered once inside a single `TabsContent`, so the native `<select>` order stays account, [target account], category (e2e relies on it).
- **Dates and status:** payment date plus the «transaction date is different» switch (a date or a period); a payment date after today (Warsaw, `todayDay()`) is always `planned` and locks «Факт»; «Позначити сплаченою» (edit of a planned operation) sets `actual` and replaces a future date with today.
- **Date fields:** `components/ui/date-field.tsx` (`DateField`) is a text field, typed as DD.MM.YYYY (dots appear by themselves, `lib/utils/date-text.ts`) with a calendar button; it reports a day key only for a real date and '' otherwise. Used for all four dates in the form instead of `type="date"`. e2e fill it with `fill('YYYY-MM-DD')` (a pasted day key is converted) and read it back as DD.MM.YYYY.
- **Undo:** delete asks first, then a toast with «Скасувати» (`lib/ui/undo-toast.ts`, 10 s). Undo of a delete re-creates the operation under its own id (`restoreTransaction`, proven on the emulator to give the same balances and rollups); undo of an edit writes the earlier operation back as a full replace (`revertTransaction`). Closing a form with changes asks first (`isDirty`).
- **Rate hint:** `useRatePreview` asks `/api/rates` (debounced); only a hint, the server stores the real conversion; an unavailable rate never blocks saving. A transfer across currencies shows the implied rate from the two amounts. `new Intl.*` stays out of the domain (formatting goes through `useFormatters`).
- **Journal:** lists planned operations too (`includePlanned` in the journal read, a «План» chip, dimmed row) but their amounts are not in the day sum. Reports, balances and the calendar still read actual operations only.
- **Tests:** unit under `tests/unit/domain/transaction-form/`, `tests/unit/api/{transaction-draft,transaction-undo,rates-client}.test.ts`, `tests/unit/ui/undo-toast.test.ts`; integration `tests/integration/ledger-restore.test.ts`; e2e `tests/e2e/transaction-form.spec.ts`.

## Journal (S08)
- **Endpoint:** `GET /api/orgs/{orgId}/journal?<filters>&cursor=&limit=` (owner, accountant, viewer; `limit` 50 by default, 100 at most; `Cache-Control: no-store`) answers `{ rows, next }`. Order: `paymentDate`, `createdAt`, document id, all descending; the cursor is an opaque string of those three values (`lib/domain/journal/order.ts`). The listing needs the three `transactions` indexes `(paymentDate, createdAt)`, `(accountId, paymentDate, createdAt)`, `(toAccountId, paymentDate, createdAt)`. Operations without `createdAt` are left out by Firestore: `scripts/check-journal-readiness.ts` finds them.
- **Scan cap:** the account and a payment-date range go through Firestore (`Filter.or` over `accountId`/`toAccountId`); every other filter (type, status, amount, category, counterparty, text, accrual date) is applied in memory while the server scans in chunks of 200. One request reads at most `SCAN_CAP` = 2000 documents; when that is spent without a full page it returns what it found and a cursor and the client asks again. Text search matches account name, counterparty name and comment, case- and diacritic-insensitive (`łódź` = `lodz`).
- **Balance after an operation** (`lib/server/journal/read.ts`, `lib/domain/journal/balance.ts`; the movement after a day, `netAfterDay`, lives in `lib/server/ledger/balance-at.ts` since S12 and is shared with the reports): the real account balance minus the effect of every later actual operation of that account, independent of the filters; planned rows get `null`. Everything newer than the newest day of the page comes from three `sum` aggregate queries over the actual operations (income, expense plus transfer out, transfer in), NOT from the rollups: Firestore cannot `sum` over a range of document ids. They need two more composite indexes, five new ones in total with the three listing indexes, in `firestore.indexes.json` (task 6). The days of the page itself come from the daily rollups `cash_{accountId}_{day}` read by an id range (account ids are Firestore auto ids and contain no `_`), and the order inside a day from the day's operations. Reads per page are measured in `tests/integration/journal-budget.test.ts`.
- **Bulk:** `POST /api/orgs/{orgId}/transactions/bulk` (`{ action: 'update' | 'delete', ids (1 to 25), patch }`; owner and accountant) runs the ids one by one through `updateTransaction`/`deleteTransaction`, one Firestore transaction per operation, and answers a result per id (`ok` or an error code); one rejection does not stop the rest. Fields: category and counterparty (income/expense only; the category needs one operation type), comment, payment date, accrual date or period; account and status are not bulk fields. The browser splits a selection into chunks of 25 (`lib/api/journal-bulk.ts`), with a stop button and an undo toast (`revertTransaction`/`restoreTransaction` from S07).
- **Browser side:** `useJournal` (`lib/hooks/useJournal.ts`: paging, infinite scroll, a fresh load when the filters change) and `useJournalSelection`; the view lives in the address (`lib/utils/journal-url.ts`: period, basis, `q`, amount, `cp`, `cat`, `types`, `status`, account); every change made in this browser (form, bulk, chip) fires a `ledger-events` event that reloads the journal. The journal does not update from other devices; the account list in the sidebar stays live. Components: `components/transactions/{JournalFilters,TransactionList,SelectionBar,BulkEditDialog,FillChip,ExportButton}.tsx`; the «вкажіть» chip fills an empty category or counterparty through the same bulk path for one row.
- **CSV** (`lib/domain/journal/csv.ts`, `ExportButton`): the browser pages the same endpoint with the current filters (at most 20 000 rows); UTF-8 with BOM, `;` separator, CRLF, decimal comma in uk/pl and a point in en, days as `YYYY-MM-DD`; a cell starting with `=`, `+`, `-`, `@` or a tab gets a leading apostrophe (formula injection). No `new Intl.*` in the domain: the number format comes from the caller.
- **Phone layout:** the toolbar selects sit in a wrapper (`order-last flex w-full sm:contents`) so below 640 px they take a row of their own; `useIsPhone` (`lib/hooks/useIsPhone.ts`, `useSyncExternalStore`, false on the server) switches to the short «all accounts/categories» labels and the short search placeholder on a phone only (pl: «Konta», «Kategorie»). A filtered empty list says «nothing matches» (`noMatchTitle`), not «no operations yet»; a planned row has a neutral grey amount; an empty category shows the «вкажіть» chip under the account name on a phone.
- **Tests:** unit `tests/unit/domain/journal/{order,filter,balance,csv,selection,bulk-input,paging}.test.ts`, `tests/unit/api/journal-*.test.ts`, `tests/unit/utils/{journal,journal-url,download}.test.ts`, `tests/unit/scripts/check-journal-args.test.ts`; integration `tests/integration/journal-{read,bulk,budget}.test.ts`; e2e `tests/e2e/journal.spec.ts`; screenshots `tests/ui-shots/journal.spec.ts` (`npm run ui:shots`).
- **Rollout guard:** `npm run check:journal -- --project=finflow-e94b5` (read-only; refuses production without the flag) lists companies where `transactions.count()` differs from `transactions.orderBy('createdAt').count()` and reads one journal page per company (unfiltered, planned, first account) so a missing composite index shows up as `FAILED_PRECONDITION` with a creation link. Deploy the indexes first (`firebase deploy --only firestore:indexes --project finflow-e94b5`) and wait until they are `READY`.

## Banks (S09)

Spec: `docs/superpowers/specs/2026-10-28-s09-banks-design.md`. Plan: `docs/superpowers/plans/2026-10-28-s09-banks.md`.

- **Connection:** the owner picks a bank (`BankPicker`); the OAuth callback (`app/api/enablebanking/callback`) verifies the signed `state` and calls `saveSession`, which writes `bankConnections/{sessionId}` (`validUntil` = the bank's `access.valid_until`, 90 days when the bank does not say) and redirects to `settings/banks?eb_connected=1`. The owner then links each bank account (`POST /api/orgs/{orgId}/bank/accounts`: an existing or a new FinFlow account, the import start day, 90 days back by default) and the first sync runs at once. A renewal re-points the linked `bankAccounts` to the new session by `identificationHashes` (else by IBAN); the link, the start day and the operation marks stay.
- **Sync step:** `syncStep` (`lib/server/banking/sync.ts`) reads ONE bank page per call, writes at most `MAX_NEW_PER_STEP` = 25 new operations and answers `done: false` while more remain. The browser loops (`syncBankAccount` in `lib/api/bank-client.ts`, at most 200 steps). A lock (`syncLock`, 60 s) makes a second run answer 409 `already_running`, which the client reports as busy, not as a failure. A run starts at `syncedThrough` minus `OVERLAP_DAYS` = 3 (banks book late), never before `importFrom`; the cursor keeps a run across steps. The last page reads the balance (`pickBalance`: closing booked, then interim booked) and, on the first sync only, fits the opening balance so the FinFlow balance equals the bank's (`fittedOpening`).
- **Dedup:** `bankTxKeys` (`lib/server/banking/key.ts`) keys each bank operation by its bank reference (`entry_reference`, else `transaction_id`) inside the bank account; without a reference it fingerprints day, amount, direction, party, text and the ordinal among identical operations of the same read. The FinFlow operation gets the deterministic id `bk_<key>` (a retry writes the same operation) and a `bankSeen/<key>` mark follows it. A deleted operation stays deleted because its mark stays. Permanent ledger refusals (future date, currency, unknown account, invalid input) write the mark with a reason and are skipped. A pending bank operation gets no mark and waits for its booked version. A client cannot send a `bk_` id: `parseTransactionInput` refuses it unless the call is internal, and `createTransaction` accepts such an id only with the matching `bankSeen` mark (that is how an undo of a deleted bank operation restores it with its provenance). A FinFlow account linked to a bank (any status) cannot be deleted (`account_linked_to_bank`).
- **Provenance and lock:** an imported operation carries a `bank` block (`accountRef`, `entryReference`, `counterpartyName`, `remittance`). `assertBankUnlocked` (`lib/domain/ledger/bank-lock.ts`) refuses `bank_locked` for a change of `type`, `status`, `accountId`, `amountMinor` or `paymentDate`; category, counterparty, comment and accrual stay editable. A transfer with bank sides (S10b) is locked per side, see «Own transfers (S10b)». The form disables the locked fields (`bank-locked-hint`) and the journal marks the row «з банку».
- **Auto-sync:** `components/shell/BankAutoSync.tsx` (owner only, in `AppShell`) syncs each linked account of a live connection whose `lastSyncAt` is missing or older than an hour, once per account per page load. A failure there is silent; the settings button retries with a message.
- **Expiry notice:** `consentNotice` (`lib/domain/banking/consent.ts`) returns 3, 2, 1 days, today or expired, counted in Warsaw days. `BankNotice` (`components/shell/BankNotice.tsx`) shows it to every member; only the owner gets the reconnect button. The status read reports a connection past its `validUntil` as expired; a bank answer of consent expired during a sync marks the connection `expired`.
- **Failures:** `classifyEbFailure` (`lib/server/banking/eb-api.ts`) maps the bank's answers to `consent_expired`, `rate_limited`, `bank_unavailable` or `bank_error`. Its patterns are a first guess; refine them from the first real failures.
- **Balance difference:** operations added or deleted by hand make the FinFlow balance differ from the bank. The settings card shows the difference and never forces it to zero.
- **Fake bank (e2e):** `tests/e2e/helpers/eb-stub.mjs` (port 4011) answers a session, account details, the interim booked balance and two transaction pages joined by `continuation_key`, with dates relative to today. `playwright.config.ts` points `EB_API_BASE` at it and generates a throw-away RSA key for `ENABLEBANKING_PRIVATE_KEY`. `EB_API_BASE` is for tests only; production uses the real API.
- **Spike:** `npm run spike:eb` (`scripts/eb-spike.ts`) reads the owner's real connection, read-only, and prints structure only (no names, amounts or IBANs). The results are in the spec, section «Результати спайку».
- **Rules:** `bankConnections` is written by the server and readable by the owner; `bankAccounts` and `bankSeen` match no rule, so clients can neither read nor write them.
- **Фонове оновлення (S09b):** `.github/workflows/bank-sync.yml` щогодини (на 7-й хвилині, UTC) викликає `POST /api/cron/bank-sync` із `Authorization: Bearer $BANK_CRON_SECRET`. `lib/server/banking/background.ts` (`runBackgroundSync`) бере активні рахунки з `collectionGroup('bankAccounts')`, пропускає ті, де `bgSlot` дорівнює поточному слоту (`backgroundSlot`: 08:00, 13:00, 17:00 за Варшавою; 17:00-07:59 це слот `#17`), де `backoffUntil` у майбутньому, `firstSyncDone` ще false або доступ минув, і викликає `syncStep` до 4 разів на рахунок. Клієнт Enable Banking створює `backgroundBankDeps()` без заголовків `psu-*` (так банк рахує запит фоновим, ліміт зазвичай 4 на добу). Слот записується до запиту до банку і витрачається будь-якою спробою (зависання банку чи вбита функція теж); `rate_limited` додатково ставить `backoffUntil` = +6 год; зайнятий рахунок (`already_running`) повертає попереднє значення `bgSlot`, а вичерпаний бюджет часу (перевіряється перед початком рахунку і перед кожним кроком 2..4) слот не витрачає. Запит до банку має таймаут 20 с (`REQUEST_TIMEOUT_MS`). Секрет відсутній або коротший за 32 символи: маршрут відповідає 503. Індекс `bankAccounts.status` (`COLLECTION_GROUP`) у `firestore.indexes.json`. Після банку той самий виклик заповнює планові платежі дня (S11, частина `recurring` відповіді; job червоніє й при `recurring.failed > 0`).

## Rules (S10)

Spec: `docs/superpowers/specs/2026-10-29-s10-auto-rules-design.md`. Plan: `docs/superpowers/plans/2026-10-29-s10-auto-rules.md`.

- **Data:** `organizations/{org}/rules/{ruleId}` `{ schemaVersion: 1, name, type: income|expense, active, order, conditions, actions: { categoryId?, counterpartyId? }, orgId, createdAt, createdBy, updatedAt }`, written only by `lib/server/rules/write.ts` (one Admin transaction with the audit entry `rule.create|update|delete|order`), readable by every member (`firestore.rules`). At most `MAX_RULES` = 50 per company (409 `limit_reached`, checked in the create transaction). Conditions (all must hold): `text` (`contains` any word, `notContains` none, `equals` one whole text; 1-20 words of 1-80 characters), `account` (1-20 FinFlow accounts), `amount` (`currency`, the company currency when the body has none; inclusive `minMinor`/`maxMinor`; never converted). The create and edit bodies are read at most 64 KB (`RULE_BODY_MAX_BYTES`, 413 above it); a rule document whose id is not a safe path segment is malformed.
- **Matching (pure, `lib/domain/rules/`):** `normalizeRuleText` (Latin diacritics folded by `foldDiacritics` in `lib/domain/text/fold.ts`, the same fold as the counterparty name key; lower case; every other run of characters one space) over the bank remittance, the bank's name for the other party and the comment, each text separately. `applyRules(rules, op)` walks the active rules by `order`, then creation time, then id; each empty field (category, counterparty) is filled by the first matching rule with that action; a field already set is never touched; `applied` lists only the rules that filled something. An action whose category was deleted or has the other type, or whose counterparty is gone or archived, is «неробоче»: `withoutUnusableActions` drops it before matching (the rule's other action still works) and `GET /rules` reports it in `unusable`.
- **Import:** `syncStep` reads the usable rules once per step (`loadUsableRules`, only when a new operation arrives) and writes each new operation through `createWithRules`; a ledger refusal caused by a rule action (`category_not_found`, `counterparty_not_found`, `counterparty_archived`) writes it again without them. The background refresh (S09b) runs the same `syncStep`. If the usable rules cannot be read, the step imports without them, so an unreadable rule never blocks a sync.
- **Trace:** an operation filled by rules carries `autoRules: [{ id, name }]` and its audit entry has `via: 'rule'`. A person's change of the category or the counterparty (form, bulk, «вкажіть» chip) removes `autoRules`; other edits keep it; an undo of a delete re-creates the operation without it. The ledger takes the trace only from the server-only `WriteExtras` of `createTransaction`/`updateTransaction` (`autoRules`, and `expectVersion` for an update: a change after the rules read the operation makes the write a `conflict`, never an overwrite); a request body cannot set them. The journal shows the chip «за правилом: назва» (`rule-chip`). Changing or deleting a rule undoes nothing.
- **Apply to existing:** `POST /api/orgs/{orgId}/rules/apply { mode: 'check' | 'apply', cursor? }` (owner, accountant) reads 200 operations per step in the journal order (the unfiltered journal index); `check` counts `{ scanned, matchOps, categories, counterparties }` and writes nothing, `apply` changes at most 25 per step through `updateTransaction`. A capped run answers `stoppedEarly`; a failed step keeps the counts it has read; leaving the dialog aborts a running apply and the result shows the partial counts. The browser loops until `done` (`checkExisting` / `applyToExisting` in `lib/api/rules-client.ts`). `POST /rules/preview { rule }` reads the latest 2000 operations in one query (Firestore cannot ask for a missing field) and counts those without a category or counterparty the draft would fill.
- **Routes:** `GET /api/orgs/{orgId}/rules` (every member; ordered, with `unusable`), `POST /rules`, `PATCH|DELETE /rules/{ruleId}`, `POST /rules/order { ids }` (all the company's listed rule ids, else 409 `conflict`; the check counts the rules the list shows), `POST /rules/preview`, `POST /rules/apply` (owner, accountant). Errors as in S06: 400 `invalid_input` with `field`, 404 `not_found`, 409 `limit_reached` / `conflict`, 422 `category_not_found` / `counterparty_not_found` / `counterparty_archived`. An action that did not change is not checked again, so an unusable rule can still be switched off or renamed.
- **UI:** settings section «Правила» (`settings/rules`, slug `rules`, visible to every member; editing needs `data.write`): the list with up/down order, the active switch and the «неробоче» badge; the editor dialog (`components/rules/RuleEditor.tsx`, «Перевірити»); «Застосувати до наявних» (`ApplyRulesDialog`: count, confirm, progress, summary). On a phone the journal shows the rule note and cuts a long rule name in the chip; the editor footer stays on screen; the reason a rule is unusable is shown as text.

## Tags (S10t)

Spec: `docs/superpowers/specs/2026-10-29-s10t-tags-design.md`. Plan: `docs/superpowers/plans/2026-10-29-s10t-tags.md`.

- **Data:** `organizations/{org}/tags/{tagId}` `{ schemaVersion: 1, name (1-50), color (a `TAG_COLORS` key: slate, sky, emerald, amber, rose, violet), excludeFromAnalytics, archived, recalcPending, orgId, createdAt, createdBy, updatedAt }`, written only by `lib/server/tags/write.ts` (one Admin transaction with the name key `tagKeys/name_{nameKeyText}` and the audit entry `tag.create|update`), readable by every member; `tagKeys` is closed to clients. At most `MAX_TAGS` = 100 per company (409 `limit_reached`, checked in the create transaction); a taken name is 409 `duplicate` with `field: 'name'` and `existingId`. No delete, only `archived`. Nothing is created automatically. The browser reads the list live (`useTags`, `lib/firebase/tags.ts`); `GET /tags` exists too.
- **Operations:** `tags` are tag ids (at most 10, none twice, `isId`). The ledger write reads every tag of the new state inside its transaction: a tag given anew must exist (422 `tag_not_found`) and not be archived (422 `tag_archived`); tags the operation already had are not checked, so an edit of something else or taking an archived tag off never fails. `excluded: true` (stored only when true, never accepted from a request) when at least one tag has `excludeFromAnalytics`; then `contributions` writes the same fields to `x_cash_*`, `x_cashcat_*`, `x_pl_*` and `balanceEffects` ignores the flag. `verifyLedger` reports `excludedDiffs`; `rebuildLedger` rewrites the flag and the `x_` documents. The journal's balance after a row reads the `x_cash_` days too. The reports skip `excluded` operations (`countsInAnalytics` in `lib/utils/analytics.ts`; the Calendar too since S10f) unless a concrete tag is chosen in the report filters (S10f); S12 shows them as the «Виключено з аналітики» line and in the reconciliation. Tags are not bank-locked.
- **Flag change:** `GET /tags/{id}/impact` counts the operations (`count()`); a `PATCH` that changes the flag of a used tag sets `recalcPending` in the same transaction and answers `recalc: true`; the browser loops `POST /tags/{id}/recalculate { cursor? }` (`recalculateTag` in `lib/api/tags-client.ts`): 100 operations a step in id order (`array-contains`, no new index), each through `refreshExcluded` (`lib/server/ledger/write.ts`, one transaction, rollups only, audit `tx.update` with `via: 'tag'`); the step that reads the last ones clears `recalcPending`. Repeating a step is safe. A tag left with `recalcPending` shows «Перерахунок не завершено» and «Продовжити» in settings.
- **Journal:** bulk `patch: { addTagIds?, removeTagIds? }` (1-10 ids each, never with other fields) runs `retagTransaction` per operation (`mergeTags`: takes off, then adds while below 10; `updateTransaction` with `expectVersion`; an unchanged list writes nothing). Filters `tg` (ids, `_none` = no tags) and `ex=1` (only excluded) work in memory. Chips per row (`tag-chip`, on a phone `tag-chip-phone`), CSV column «Теги» (names joined by `, `).
- **Rules:** action `tagIds` (1-5) next to the category and the counterparty. Tags are added, never removed: the union of the operation's tags and the tags of every matching rule, in rule order, at most 10. One missing or archived tag makes the whole tag action «неробоче»; an edit checks only the tags it adds. Import writes again without the rule on `tag_not_found`/`tag_archived`. «Застосувати до наявних» counts `tags`; «Перевірити» counts operations that lack a tag of the rule too.
- **UI:** settings section «Теги» (`settings/tags`, slug `tags`, every member sees it, editing needs `data.write`); `components/tags/{TagDot,TagPicker,TagChips,TagEditor,TagRecalcDialog}.tsx`; the form field «Теги» (`components/forms/transaction/TagsField.tsx`, a new tag can be created from it) is owned by the form now (`FormOwnedDraft` keeps only project and files out). The colours are the `--color-tag-*` tokens (`lib/ui/tag-colors.ts`).
- **Rollout guard:** `npm run check:tags -- --project=finflow-e94b5` (read-only; refuses production without the flag) lists the operations whose `tags` are not tag ids; it must report none before the deploy.
- **Tests:** unit `tests/unit/domain/tags/*`, `tests/unit/domain/ledger/excluded.test.ts`, `tests/unit/domain/rules/tags.test.ts`, `tests/unit/api/tags/routes.test.ts`, `tests/unit/api/tags-client.test.ts`, `tests/unit/server/tags/http.test.ts`, `tests/unit/scripts/check-tags.test.ts`; integration `tests/integration/{tags-write,ledger-tags,tags-recalc,journal-tags,rules-tags}.test.ts`; rules in `tests/rules/`; e2e `tests/e2e/tags.spec.ts`; screenshots `tests/ui-shots/tags.spec.ts` (`playwright.shots.config.ts`).
- **Tests:** unit `tests/unit/domain/rules/*` (incl. the acceptance fixture `fixture.ts`: 300 Polish bank rows and 10 rules leave 48 of 300 = 16.0% without a category: 44 one-off counterparties (42 generated, plus BPH LEASING and KWIACIARNIA ZUSZKA, which test the substring hazards), 2 Allegro refunds, 2 income refunds; a modelled small-business mix, not a measurement of real data; the fuel rule words are `ORLEN`, `BP STACJA`, `SHELL`, a bare `BP` is not used because it matches BPH, documented in `substring.test.ts`), `tests/unit/api/rules/*`, `tests/unit/api/{rules-client,rule-draft}.test.ts`; integration `tests/integration/{ledger-auto-rules,rules-write,rules-import,rules-apply}.test.ts`; rules in `tests/rules/`; e2e `tests/e2e/rules.spec.ts` (bank seeds in `tests/e2e/helpers/bank-seed.ts`). ## Own transfers (S10b)

Spec: `docs/superpowers/specs/2026-11-01-s10b-own-transfers-design.md`. Plan: `docs/superpowers/plans/2026-11-01-s10b-own-transfers.md`.

- **Data:** no new collections, indexes or rules. A transfer may carry `bank` (its outgoing side came from a bank), `bankTo` (`{ key, accountRef, entryReference?, counterpartyName?, remittance? }`: the incoming side was the bank income `bk_<key>`; its amount, currency and day are the transfer's `toAmountMinor`, `toCurrency`, `toDate ?? paymentDate`) and `toDate` (the day the money arrived on `toAccountId`, stored only when it differs from `paymentDate`, at most `MAX_ARRIVAL_DAYS` = 7 days away). Only the server writes them; a malformed `toDate`/`bankTo`, or either on an income or expense, makes the document unreadable (`verifyLedger` lists it as uncountable). `datedEffects` (`lib/domain/ledger/effects.ts`) is the one owner of «which account, which day, how much»: the money in of a transfer counts on `receivedOn(tx)` in the `cash_`/`x_cash_` rollups and in the journal's balance after a row (`dayOpsQuery` adds `toDate == day`, `arrivalShift` corrects the sums by payment day from the transfers paid within 7 days, no new index); the balances never depend on the day.
- **Pure rules (`lib/domain/ledger/transfer.ts`):** `bankSideOf` (an actual, non-recurring bank income or expense under its `bk_` id that pays no planned occurrence, `seriesId`, S11), `convertToTransfer` (an expense of A → A→B, an income of A → B→A with `bankTo`; one currency, B ≠ A), `mergeToTransfer` (a bank expense of A and a bank income of B → A→B under the expense id, both banks' real amounts, equal amounts in one currency, at most 7 days apart, tags merged to 10 with the dropped ones counted), `splitTransferSides` (back to the bank operations without a category; the income on its arrival day with the bank text as comment). Category, counterparty, accrual, rates and `autoRules` do not survive a conversion. `combineChanges` adds the change sets of one transaction.
- **Ledger (`lib/server/ledger/transfer.ts`):** `makeTransfer` (`convert` or `pair`, ONE Admin transaction through `applyChange`, audit `tx.update`/`tx.delete` with `via: 'transfer'`) and `splitTransfer` (a side in another currency gets its rates again before the transaction, which then requires the version read before, else `conflict`; the income is re-created under `bk_<key>`, audit `tx.create` with `via: 'transfer'`). A conversion refuses a target linked to a bank (`not_eligible` on `toAccountId`: that bank brings its own side); a merge needs the `bankSeen` mark of the income (it keeps the sync from importing it again; the sync only adds keys it has no mark for and never updates an operation). New code `not_eligible` (422).
- **Bank lock:** `assertBankUnlocked` keeps the type and every bank side: `bank` locks `accountId`, `amountMinor`, `paymentDate`; `bankTo` locks `toAccountId`, `toAmountMinor` and `toDate ?? paymentDate`; the other account, tags and comment stay editable. `updateTransaction` carries `bank`, `bankTo` and `toDate` from the prior document (`withBankSides`). The form locks the whole amount block of a bank transfer and offers «Розділити переказ» (`split-transfer`).
- **Undo of a delete:** a bank transfer comes back through the create route with `toDate` and `bankToKey` (internal create keys, never in a PATCH; `bankRestoreOf` in `lib/api/transaction-undo.ts`); `createTransaction` takes both bank blocks from the `bankSeen` marks only (`bankSidesOf`) and refuses a side that lives on already (its own operation exists or another transfer's `bankTo.key` holds it), so nothing counts a bank operation twice.
- **Suggestions:** `GET /api/orgs/{orgId}/transfers/suggestions` (every member) reads the operations of the last 90 days by `paymentDate` (at most 2000, selected fields, filtered in memory) and answers `{ pairs, total, ambiguous, truncated }`: a bank expense and a bank income of two accounts, same amount and currency, at most 3 days apart, each side with exactly one candidate, newest first, at most 50, each side with its version (`<seconds>.<nanoseconds>`). Turned-down pairs live in this browser only (`localStorage` `finflow:transfer-dismissed:<org>`, the newest 500). The journal reads them on load, when the dialog opens and after a transfer action (`finflow:transfers-changed`), never after an ordinary edit.
- **Routes:** `POST /api/orgs/{orgId}/transfers` with `{ pairs: [{ fromId, toId, versions }] }`, `{ merge: [a, b] }` or `{ convert: { ids (1-25), toAccountId } }` (owner, accountant; 64 KB) answers a result per pair or id (`ok` with `id`, `deletedId`, `droppedTags`, `before`, or a ledger code: `conflict`, `not_eligible`, `currency_mismatch`, `invalid_input`, `account_not_found`, `not_found`, `ledger_busy`, `unknown`); `POST /transfers/{txId}/split` (no body) answers `{ restored }`.
- **UI:** the journal banner (`transfer-suggestions`) and its dialog (`components/transactions/TransferSuggestions.tsx`: every pair ticked, failed pairs stay with the reason), «Зробити переказом» (`ConvertTransferDialog`) and «Об’єднати в переказ» in the selection bar (offered only for a selection `convertSourceOf`/`mergePairOf` accept), one undo toast for all of them (split, then the operations written back as they were); a bank transfer row has «з банку» and «зарахування <day>» (`transfer-arrival`, on a phone `transfer-arrival-phone`).
- **Rollout guard:** `npm run check:transfers -- --project=finflow-e94b5` (read-only; refuses production without the flag) counts per company the pairs, ambiguous sides and bank operations the suggestions see and the transfers that carry a bank side, and runs each new query shape once (a missing index shows as `FAILED_PRECONDITION`).
- **Tests:** unit `tests/unit/domain/ledger/transfer*.test.ts`, `tests/unit/domain/transfers/*`, `tests/unit/domain/journal/arrival.test.ts`, `tests/unit/api/transfers/routes.test.ts`, `tests/unit/api/{transfers-client,transfer-undo}.test.ts`, `tests/unit/server/transfers/run.test.ts`, `tests/unit/scripts/check-transfers.test.ts`; integration `tests/integration/{ledger-transfers,ledger-transfer-split,journal-transfers,transfers-read}.test.ts` (helper `transfer-helpers.ts`); e2e `tests/e2e/transfers.spec.ts` (seed `helpers/transfer-seed.ts`); screenshots `tests/ui-shots/transfers.spec.ts` (`playwright.shots.config.ts`).

## Report filters (S10f)

Spec: `docs/superpowers/specs/2026-11-02-s10f-analytics-filters-design.md`. Plan: `docs/superpowers/plans/2026-11-02-s10f-analytics-filters.md`.

- **Data:** since S12 the same filters are the query of the server reports (`GET /reports/cashflow|pl`, strictly parsed by `parseReportQuery`); only the Calendar still filters the operations it reads (`useTransactions`).
- **Address:** `lib/domain/analytics-filter/filter.ts` (pure): `AnalyticsFilters` (`types` = whole groups `income`/`expense`/`transfer`; `categoryIds` = categories of any depth and the uncategorised rows `_none:income`, `_none:expense`, matched exactly; `counterpartyIds`, `tagIds`, `accountIds`), `parseAnalyticsFilters` / `analyticsFiltersToParams` with the journal's names `types`, `cat`, `cp`, `tg` (`_none` = no tags) and `accounts` (comma-separated; invalid ids, types and repeats dropped, at most `MAX_FILTER_IDS` = 30 per list, other parameters not read). `useAnalyticsFilters(scope)` (`lib/hooks/`) reads them, drops the ids the company does not have (`knownAnalyticsFilters`; a list still loading keeps its ids; archived rows count as known) and writes them back with `router.replace` (no scroll); the period stays a page choice outside the address. `AnalyticsNav` links carry the filter parameters (`analyticsHref`), so the choice follows the report tabs and can be shared; the module tab and the analytics index open the reports without filters.
- **Matching:** the shared choice rule is `matchesSharedChoices` (`lib/domain/journal/filter.ts`): counterparties, accounts (the account or a transfer's target) and tags «any of the chosen», `_none` the operations without tags. The journal adds its own kind rule, AND of types and categories (`matchesJournalKinds`; `matchesSelection` = both). The reports add the union of the payment tree (`matchesAnalyticsKinds`, `lib/domain/analytics-filter/kinds.ts`); `matchesAnalyticsSelection` composes it with the shared rule. Union: a chosen group matches all its operations (uncategorised and later categories too), a chosen category its own operations, a parent its descendants (the dialog ticks them), `_none:<type>` the operations of that type without a category. An operation's row is `kindRowOf` (`kinds.ts`, the one rule the P&L shares): its category while the company has it with the operation's own type, else its type's `_none` row (a deleted category and a category of the other type count as uncategorised). `matchesAnalyticsKinds` and `filterForAnalytics` take the company's `categoryTypes` (`categoryTypesOf`; `useAnalyticsFilters` returns them, `undefined` while loading, when the stored ids stand); nothing chosen matches everything. `filterForAnalytics` returns `{ operations, includeExcluded }`: a concrete tag makes the reports count the operations excluded from analytics (Finmap's rule). the server reports and `buildCalendar` take that selection whole and return `excludedCounted` (the Calendar: `{ days, excludedCounted }`; `includesExcluded` is the one rule of a concrete tag); the page shows «Показано також операції, виключені з аналітики» (`analytics-excluded-hint`) only when the report shown counted an excluded operation. `countsInAnalytics` (`lib/domain/analytics-filter/filter.ts`) is the one predicate (the Calendar's day list uses it too). The Balance applies only the accounts (`filterAccounts` on the list given to `BalanceSheet` and to its CSV); the Cash Flow and P&L CSV are built from the filtered reports.
- **Tree:** `kinds.ts` (pure, one owner of the tree): `buildKindTree` (one group per type, any depth; a missing parent, a parent of the other type or a loop makes a root; members in the caller's order, which the dialog and the hook share), `kindState` (tri-state derived from the stored choice and the tree, never stored), `toggleKind` (a group, a category with its subtree, an uncategorised row or a transfer; refused above 30 ids, not cut), `normaliseKinds` (a group with at least one category, all of them and its `_none` row chosen, is stored as its type; a group without categories never is; every type chosen is no restriction), `topChoices` (the rows the field's summary counts: a parent with its child is one row). `useAnalyticsFilters` applies the normal form once the categories are loaded; the dialog's write path gets it from `toggleKind`.
- **UI:** `AnalyticsFiltersButton` (`components/analytics/AnalyticsFilters.tsx`: the pill «Фільтри» with the number of fields in use, `analytics-filters-count`; in `ReportToolbar` on Cash Flow and P&L, above the Calendar, next to the Balance's date select) opens `AnalyticsFiltersDialog`: «Види платежів і категорії» as one tree (the root «Усі види платежів і категорії» is checked while nothing is restricted and dashed otherwise; the groups «Усі надходження» and «Усі витрати» with their categories, collapsible, and a «Без категорії …» row each; «Переказ»; the closed field reads «Усі види і категорії», the group or category name, or «Вибрано: N»), «Контрагенти», «Теги» (with «Без тегів» last), «Рахунки» (the Balance shows only this one). Each field is a `FilterMultiSelect` in Finmap's form («Теги (N)», a search, «Усі …» first, a checkbox row per value, «Вибрати»), opened inline one at a time; ticks go to the dialog's draft at once, «Вибрати» and Esc close the list, «Готово» writes the address, «Скинути фільтри» clears the fields the dialog shows and applies. The S10t highlight rule (`highlightedRow`, `lib/ui/highlight.ts`) is shared with `TagPicker`: nothing is highlighted until typing, an arrow or a real pointer move, so Enter never ticks a row by accident. Tree rows are the same list: `state` (checked; `mixed` is the dash, exposed as `data-state`), `level` (indent), `expanded` with an arrow (ArrowRight and ArrowLeft open and close the highlighted row only while the search is empty; with a search typed they move the caret), `onRowToggle` for the owner's rule. A tree is `role="tree"` with `treeitem` rows (`aria-level`, `aria-expanded`, `aria-checked`; the option role has no level or expanded state); a partly chosen row's name says «частково вибрано». A tree is never cut at 100 rows (`listWindow`, `lib/ui/filter-list.ts`). A tick the 30-id limit refuses shows «Не більше 30 у списку» (`refused`) until the next tick that is kept. Archived tags and counterparties are offered, muted; deleted categories are pruned from the address (their operations stay under «Без категорії»).
- **Tests:** unit `tests/unit/domain/analytics-filter/filter.test.ts` and `kinds.test.ts` (tree, union, tri-state, toggle, normal form), `tests/unit/utils/analytics.test.ts` (block «report filters (S10f)»), `tests/unit/domain/journal/filter.test.ts` (`matchesSelection`), `tests/unit/ui/highlight.test.ts`, `tests/unit/ui/filter-list.test.ts`, `tests/unit/shell/analytics-sections.test.ts`; e2e `tests/e2e/analytics-filters.spec.ts`; screenshots `tests/ui-shots/analytics-filters.spec.ts` (`playwright.shots.config.ts`).

## Planned payments (S11)

Spec: `docs/superpowers/specs/2026-11-10-s11-planned-payments-design.md`. Plan: `docs/superpowers/plans/2026-11-10-s11-planned-payments.md`.

- **Data:** `organizations/{org}/recurring/{id}` `{ schemaVersion: 1, name (1-80), kind income|expense, accountId, categoryId?, counterpartyId?, tags (≤ 10), description?, amountMinor, currency (the account's), estimated, frequency weekly|monthly|everyNMonths|yearly, interval (everyNMonths 1-24, else 1), dayOfMonth (1-31, null for weekly), weekday (ISO 1-7, weekly only), startDate, endDate?, weekendRule none|next|previous, preset? zus|pit4|vat7, status active|paused, generatedThrough?, dueOn?, orgId, createdAt, createdBy, updatedAt, updatedBy, version }`, at most `MAX_SERIES` = 100 (409 `limit_reached`); `kind` and `preset` are fixed at creation. One validation for bodies and stored documents (`parseSeriesInput`). An occurrence is an ordinary planned operation `pl_<seriesId>_<occurrence>` with the server-only fields `seriesId`, `occurrence` (the nominal day), `estimated`, `manual` (`lib/domain/ledger/doc.ts`; a request with them is `400`; `pl_` ids are reserved like `bk_`). `isRecurring` stays the form's own flag: the generator never sets it. `recurringDone/{planId}` `{ seriesId, occurrence, reason paid|skipped|deleted, txId?, estimated, manual, plan?, carried?, planCreatedAt?, planCreatedBy?, at, by }` is closed to clients.
- **Schedule (pure, `lib/domain/recurring/schedule.ts`):** UTC day strings only (no summer time shift); the first occurrence is the first rule day on or after `startDate`; a shorter month takes its last day (31 → 28/29); everyNMonths and yearly keep the phase of the start month; `paymentDayOf` moves a weekend or Polish holiday by `weekendRule` (`lib/utils/pl-calendar.ts`); `periodOf` is the week, month, block or year an occurrence pays for.
- **Generator:** `createSeries` fills today to `windowEnd(today)` (three months, `addMonthsClamped`); `fillSeries` (the daily step) fills from the day after `generatedThrough`, so missed days come back as overdue plans, at most 100 per series and call; an occurrence is created only when neither its operation nor its mark exists (`t.create`, deterministic id), and `dueOn` is checked inside the transaction, so parallel runs fill once. A deleted category or an archived counterparty or tag of the series is left out of new plans; a missing account fails the series. Created plans are written by `system`, audit `tx.create` with `via: 'plan'`.
- **Daily step:** `POST /api/cron/bank-sync` runs the bank refresh first, then `runRecurringCron` (`lib/server/recurring/cron.ts`) with `min(10 s, 55 s − elapsed)`: the due series by `collectionGroup('recurring').where('dueOn', '<=', today).orderBy('dueOn')` (at most 200), each in its own transaction, the budget checked before each; a lasting failure moves `dueOn` to tomorrow, `ledger_busy`/`conflict` retry next hour. The answer has `recurring: { considered, filled, created, skipped, failed }`; `.github/workflows/bank-sync.yml` fails on `recurring.failed > 0`.
- **Change of a series (`updateSeries`, one transaction):** paused = no new plans (`removeFuture` deletes the future unpaid ones); active = the future unpaid plans not changed by hand follow the new schedule and content (same occurrence updated, a vanished one deleted without a mark, a new one created), never in a period a mark or a kept operation (paid, manual, past) already takes (`takenPeriods`: the marks and the kept operations from `takenFrom` on, the one bound of the rewrite, `plan.ts`; index `recurringDone (seriesId, occurrence)`); at most `REWRITE_CAP` = 100 future operations (409 `limit_reached`, `field: 'planned'`). Delete (`?future=delete|keep`, delete by default): paid and past stay with `seriesId`, the marks stay. A person's change of a field the series sets on a planned occurrence makes it `manual` (`withSeries`); a new amount also drops `estimated`. A series' account cannot be deleted or change currency (`account_has_operations`, `field: 'recurring'`).
- **Marks (`markChangeOf`, inside `commit`):** «Позначити сплаченою» (planned → actual) writes `paid` with `txId` = the operation; back to planned lifts it; a person's delete of a planned occurrence writes `deleted`; a create under a `pl_` id (the undo of a delete or of «Пропустити») is accepted only from a `skipped`, `deleted` or self-`paid` mark, takes the series fields from it and lifts it; a retry after it went through is a replay. Deleting an actual occurrence keeps `paid`.
- **Plan → fact:** `GET /recurring/suggestions` (every member) reads the planned series occurrences not changed by hand from 90 days back to 3 days ahead (`status, paymentDate` index, at most 500), and only then the bank operations of the days they span (at most 2000, S10b's query shape); a pair is the same kind and account, the bank day from −3 to +10 days of the plan's payment day, the exact amount, or for an estimate the same counterparty; each side with exactly one candidate; newest first, at most 50, with versions and the series name. `POST /recurring/matches { confirm | undo }` (owner, accountant) runs one transaction per pair: the bank operation keeps its id, amount, day, bank block, `bankSeen` mark and rules trace, takes the category, counterparty, tags and comment it lacks and the series link; the plan is deleted; `paid` keeps the plan's document and what was carried; the undo restores the plan exactly and takes off only what is still as carried. A bank operation with `seriesId` is never suggested again and is no side of a transfer (S10b). Turned-down pairs live in this browser (`finflow:plan-dismissed:<org>`).
- **Routes:** `GET|POST /api/orgs/{orgId}/recurring` (overview; create 201), `GET|PATCH|DELETE /recurring/{seriesId}`, `POST /recurring/{seriesId}/skip { occurrence }` (`{ before }`), `GET /recurring/suggestions`, `POST /recurring/matches`; writes owner and accountant, reads every member; 64 KB bodies; `RecurringError` (400 with `field`, 404, 409) in `lib/server/recurring/http.ts`, ledger codes through `toHttpError`; a path id that cannot be an id is 404.
- **Reads:** `GET /recurring` (`readOverview`) = the series, `count()` of overdue planned operations (all, not only series), the oldest 50, and the planned operations of today to the window end (at most 1500): «Наступна дата» is a series' first plan, else its first occurrence after `generatedThrough`; «Найближчі 7 днів» sums income and expense per currency. No `nextOccurrence` field.
- **UI:** module tab «Планові платежі» (`/[org]/recurring`): the strip (`recurring-overdue`, `recurring-soon-*`), the series (`series-row`, «Змінити», «Призупинити»/«Відновити», «Видалити» with the future plans choice), «Додати серію» and «Додати з пресету» (`preset-menu`, `preset-zus|pit4|vat7`: ZUS 15, PIT-4 20, VAT-7 25, estimated, next business day, the S06 counterparty), the upcoming plans as cards (`planned-row`, «Позначити сплаченою», «Перенести», «Пропустити», each with an undo toast). Journal: `overdue-chip` on a planned row whose day passed, the banner `plan-matches` and its dialog (`plan-match`). Form: `series-hint` («з серії …», the warning that a change detaches it).
- **Rollout guard:** `npm run check:recurring -- --project=finflow-e94b5` (read-only; refuses production without the flag) runs each new query shape once (due series, overdue count and list, the window, plan candidates and bank days, a series' operations and marks) and prints counts per company; a missing index shows as `FAILED_PRECONDITION`.
- **Rules and indexes:** `firestore.rules`: `recurring` is readable by every member (`'recurring'` joins the member read list), `recurringDone` matches no rule (closed). `firestore.indexes.json` adds `transactions (status ASC, paymentDate ASC)` (overview and plan candidates), `transactions (seriesId ASC, paymentDate ASC)` (a series' operations), `recurringDone (seriesId ASC, occurrence ASC)` (occupied periods) and a `recurring.dueOn` field override for the collection group (the daily step). The emulator needs none of them; production does, so the indexes deploy first and `check:recurring` runs after they are `READY`.
- **Gotchas:** `isRecurring` is the form's own flag and the generator never sets it; `bankSideOf` refuses an operation with `seriesId` too. Any person's change of a field the series sets (type, account, amount, date, category, counterparty, description, tags) makes the planned occurrence `manual` and the series stops following it; a new amount also drops `estimated`. Days are UTC `YYYY-MM-DD` strings, but «today» for the window and the due check is the Warsaw day (`deps.today()`). A `pl_` id is reserved: clients cannot create one, only the undo of a delete or «Пропустити» can, with its mark. An undo of a deleted bank operation that paid a plan returns it without `seriesId` (the mark keeps the occurrence paid).
- **Tests:** unit `tests/unit/domain/recurring/*` (schedule incl. DST and holidays, input, documents, fill and rewrite plan, matching, overview, editor, rows, property test of daily fills), `tests/unit/domain/ledger/series.test.ts`, `tests/unit/server/recurring/*`, `tests/unit/api/recurring/routes.test.ts`, `tests/unit/api/cron/bank-sync.test.ts`, `tests/unit/api/recurring-client.test.ts`, `tests/unit/scripts/check-recurring.test.ts`; integration `tests/integration/{ledger-plan-marks,ledger-series,ledger-plan-match,recurring-read}.test.ts` (helper `recurring-helpers.ts`); rules in `tests/rules/`; e2e `tests/e2e/recurring.spec.ts` (seed `helpers/recurring-seed.ts`); screenshots `tests/ui-shots/recurring.spec.ts` (`playwright.shots.config.ts`).

## Server reports (S12)

Spec: `docs/superpowers/specs/2026-11-11-s12-reports-design.md`. Plan: `docs/superpowers/plans/2026-11-11-s12-reports.md`.

- **Split:** `lib/domain/reports/` is pure. `query.ts`: the strict report address (`from`, `to` up to `MAX_REPORT_DAYS` = 3660 days, and the S10f filters `types`, `cat`, `cp`, `tg`, `accounts`; an unknown, repeated or malformed parameter, or a filter value the lenient S10f reader would drop, is `400 invalid_input` with `field`). `facts.ts`: the facts of a report in one shape for both paths. `cashflow.ts`: days up to 31 days, months above. `pl.ts`: by recognition date; a period of recognition is spread by `allocatePeriod`, a partial month by its days (`accrualShare`, cents rounded half away from zero). `reconcile.ts`, `balances.ts`, `categories.ts` (the tree from `buildKindTree`), `export.ts` (sheets and CSV sections). `lib/server/reports/`: `read.ts` and `balances.ts` (reads), `rates.ts` (NBP per request), `xlsx.ts` and `file.ts` (the file, words from `lib/i18n/report-labels.ts`), `http.ts` (`ReportError` to HTTP), `index.ts` (`reports`, the production dependencies). Browser: `lib/api/reports-client.ts`, `lib/hooks/useReports.ts`, `lib/utils/report-view.ts`.
- **Two paths, one function:** without filters over whole months the figures come from the rollups (`cash_`/`x_cash_` of the chosen accounts by id range; `cashcat_` or `pl_` per month), `coverage.source = 'rollups'`. Otherwise they come from the operations of the period (`status, paymentDate`; the P&L also `accrual.date` and `accrual.to`), recomputed with the ledger's own `contributions`, `coverage.source = 'operations'`. Both become `ReportFacts` (`factsFromRollupDocs`), and `buildCashFlowCore` / `buildPLCore` take only those facts. A property test checks rollups = operations. No new index: the operations queries use the S11 `transactions (status, paymentDate)` index and the automatic single-field indexes of `accrual.date` and `accrual.to`.
- **Read cap:** `REPORT_SCAN_CAP` = 10 000 documents (operations and rollups) per request. Each request counts its queries first (`count()`, in the same snapshot); above the cap the answer is `422 too_many_operations` with `cap`, with no document read; otherwise it reads exactly the counted number (`limit(count)`), so a figure is never partial. A filtered P&L reads the period's payments (for the reconciliation) and its accruals, so it reaches the cap at about half the operations of a filtered Cash Flow. All reads of one request are one read-only transaction (`readSnapshot`, `lib/server/ledger/reader.ts`). Responses are `Cache-Control: no-store`; there is no response cache (no ledger version exists to validate one).
- **Reconciliation equation:** opening (close of `from − 1`, at most today) + net of the report + excluded from analytics (null when a concrete tag counts them in) + outside the filter + transfers (in PLN at the NBP rate of their day) + exchange difference = closing (close of `min(to, today)`). What does not add up is the «Розбіжність» line, never rounded away or absorbed by the exchange difference. The exchange difference is (opening + movement) at the closing rate − opening at the opening rate − the movement at its own rates. Balances at a day come from `balancesAt` (`lib/server/ledger/balance-at.ts`, shared with the journal): the account balance minus three `sum` aggregates after the day, plus the arrival shift of transfers. Operations that cannot be counted (another currency without `base`) are `coverage.uncountable`, never a zero; the rollup path reports `uncountable: null` (unknown).
- **FX rules (S04 `resolveRate`):** movements are valued at their stored `base` (incomes and expenses) or at `resolveRate(currency, PLN, day)` (transfers); a balance at the close of day D is valued at `resolveRate(currency, PLN, D + 1)`, the last table published on D or before. `quoteRates` keeps one lookup per (currency, date) pair per request, dropped with the response. An `FxError` for one pair does not fail the report: the currency goes to `missingRates`, the PLN lines that need it become `null` (`valued: false`), and the report's own figures stay. `final: false` (today's table may still be published) shows a note.
- **Routes:** `GET /api/orgs/{orgId}/reports/cashflow|pl?from=&to=&<filters>`, `…/balances?date=`, `…/export?report=cashflow|pl&format=csv|xlsx&<same query>`. Every member may read; `400 invalid_input` (with `field`), `401`, `403`, `422 too_many_operations` (with `cap`) through `lib/server/reports/http.ts`. The home address `/[orgSlug]` has no page or handler: a plain 404.
- **Export:** built from the same report in the app's language (`NEXT_LOCALE`, else `Accept-Language`, else pl). Sheets «Звіт», «За категоріями», «Звірка» (translated in `lib/i18n/report-labels.ts`). CSV uses the journal's rules (`buildCsvSections`: BOM, `;`, CRLF, decimal comma in uk/pl, formula guard). XLSX is written in memory by `write-excel-file` pinned to exactly `4.1.1` (MIT, one dependency `fflate`); amounts are numbers, a text starting with `=` stays text (only `type: 'Formula'` writes a formula). `fflate` 0.8.3 is a dev dependency for tests that read the file back. `write-excel-file/node` is in `SERVER_CJS_MODULES` (`check:server-imports`).
- **UI:** Cash Flow and P&L read the server (no `useTransactions`): `ReportSource` (`report-source`, `data-source`), `ExcludedLine` (`cashflow-excluded`, `pl-excluded`), by account (`cf-account-row`), by category (`cf-category-row`), `ReconciliationBlock` (`reconciliation`, `recon-*`), `ReportNotice` (`report-too-large`, `report-error`), the buttons «Експорт CSV» and «Експорт XLSX». «Баланс»: server balances at «Станом на» (today, end of last month, end of last quarter, end of last year), totals in PLN at NBP rates. The Calendar still reads operations (S13); the sidebar stays a live subscription.
- **Rollout guard:** `npm run check:reports` (read-only). Without a target it refuses; under the emulator run `npx firebase emulators:exec --only auth,firestore --project demo-finflow "npm run check:reports"`; production needs `-- --project=finflow-e94b5` (nothing is read without the flag). Rates come through a read-only view of the NBP cache. It builds this month's Cash Flow and P&L from both paths, and yesterday's balances per company, runs each new query shape once (`FAILED_PRECONDITION` would show a missing index), and prints counts only: whether rollups = operations and whether the reconciliation adds up. Exit 0 all read, 1 a read failed, 2 refused or bad arguments.
- **E2e NBP stub:** `NBP_API_BASE` (tests only, like `EB_API_BASE`) points `fetchNbpTables` at `tests/e2e/helpers/nbp-stub.mjs` (port 4012, the Playwright `webServer` and `playwright.config.ts`); unset means the real NBP.
- **Gotchas:** the home address is a route handler because a page's `notFound()` after the Firestore read answered `200` in `next dev`. Its `404` versus `307` is an existence oracle for any caller, signed in or not (the proxy checks sessions only on `/<segment>/...`); known, see PROGRESS.md S12. Do not reintroduce `buildCashFlow`, `buildPL` or `exportToCSV` in the browser: the report builders live in `lib/domain/reports/`. A report answers with `coverage.source`; never mix the two paths in one response.
- **Tests:** unit `tests/unit/domain/reports/*` (with `property.test.ts`), `tests/unit/server/reports/*`, `tests/unit/api/reports/routes.test.ts`, `tests/unit/api/reports-client.test.ts`, `tests/unit/utils/report-view.test.ts`, `tests/unit/i18n/report-labels.test.ts`, `tests/unit/scripts/check-reports.test.ts`; integration `tests/integration/{balance-at,reports-read,reports-balances}.test.ts` (helper `report-helpers.ts`); e2e `tests/e2e/reports.spec.ts` (seed `helpers/report-seed.ts`); screenshots `tests/ui-shots/reports.spec.ts`; measurement `scripts/measure-reports.ts` (emulator only).
